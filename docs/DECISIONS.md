# VAD Massage Booking V2 — Decision Log

Updated: 2026-09-23. These are design decisions and intended requirements; implementation status belongs in `APP_PLAN.md`. Add dated entries when a decision changes, retaining earlier context.

## ADR-001 — One booking core, separate interfaces

**Decision:** Keep one Supabase-backed booking system and shared server-side rules, with distinct client and admin experiences in the same repository initially.

**Reason:** A client, Vad and a future messaging agent must receive the same availability, pricing and booking outcomes. Separate navigation and permission boundaries serve each role without synchronizing independent calendars.

## ADR-002 — Booking authority resides in the backend

**Decision:** The backend owns slot calculation, quotes, eligibility, holds, booking creation and changes. Revalidate and reserve atomically when confirming a booking.

**Reason:** Browser and conversational interfaces cannot safely enforce rules or prevent two requests taking the same slot. Meaningful tests must cover boundaries and conflicts.

## ADR-003 — Clients, accounts and channels are distinct

**Decision:** A client record can exist without an online account, booking or Telegram/WhatsApp connection. A normalized phone can help find a client; confirm saved address and verify identity for sensitive actions.

**Reason:** Vad creates client records offline, and contact details can change or be shared.

## ADR-004 — Agent-ready API without immediate Meta dependency

**Decision:** Design controlled booking operations that the website, admin and future approved integrations can call. Grant a client-facing WhatsApp agent only its necessary actions; any personal assistant uses separate admin-scoped access. Verify Meta Business Agent, Muse and WhatsApp Business Platform capabilities before choosing an integration.

**Reason:** Product access and APIs can change. The booking system must remain usable and authoritative regardless of an AI provider.

## ADR-005 — Payment and appointment state are explicit

**Decision:** Bank transfer instructions, verification, booking hold and confirmed appointment are separate concepts. A quoted or requested session is not automatically a paid booking.

**Reason:** Manual payment verification and hold expiry must be represented accurately in the app and notifications.

## ADR-006 — Documentation stays with implementation

**Decision:** Keep `docs/APP_PLAN.md` for scope, behavior and roadmap, and `docs/DECISIONS.md` for reasons behind architectural choices. Read both before substantial V2 changes and update them in the same change when decisions or status shift.

**Reason:** Repository history is easier to inspect than decisions scattered across chats. Status must be supported by code and acceptance evidence.

## ADR-007 — External agents are interfaces, not booking systems

**Decision:** Website, Admin, WhatsApp and any future Meta/Muse agent must call the same authoritative booking operations. External agents may not implement their own availability, pricing, booking-limit or conflict logic and may not write booking tables directly.

**Reason:** This prevents channel-specific behavior drift and allows an agent provider to be changed without changing the booking rules.

## ADR-008 — Agent writes require confirmation, idempotency and audit

**Decision:** Agent-triggered create/reschedule/cancel actions require explicit client confirmation, an idempotency/request key and an auditable source/actor record. Webhook or tool retries must be safe to repeat without duplicate bookings or duplicate mutations.

**Reason:** Messaging platforms and AI/tool calls can retry or repeat requests. A booking system must not interpret repeated delivery as repeated intent.

## ADR-009 — Channel identity does not replace canonical client identity

**Decision:** `clients.id` is the canonical business identity. Auth user IDs, phone numbers, WhatsApp identities, Telegram connections and other channels link to it. Phone-number matching may help identify a returning client but is not sufficient authorization for sensitive reads or changes.

**Reason:** Phone numbers can change, be shared or be entered incorrectly. Client history and booking changes need a stable record and stronger authorization boundaries.

## ADR-010 — Build agent readiness now; integrate Meta/Muse later

**Decision:** V2 will include a channel-neutral, versioned integration boundary, separate permission scopes, source/actor audit, idempotent commands and committed-event notification hooks as part of the core architecture. Actual Meta/Muse/WhatsApp agent implementation remains deferred until the core booking journeys are reliable and the current provider capabilities are verified.

**Reason:** These boundaries are inexpensive to design into the clean rebuild but expensive to retrofit after the database and booking contracts are established. They also avoid making V2 dependent on a particular external AI product.


## ADR-011 — Bounded reads and on-demand Admin loading

**Decision:** Calendar and operational reads must be scoped to the date/data range needed by the current screen. Historical data loads separately. Analytics, detailed Settings, receipts/documents and similarly heavy secondary surfaces should be lazy-loaded when opened.

**Reason:** V1 repeatedly loaded all bookings and bundled heavy Admin surfaces into the initial workspace. That increased database traffic, render work and coupling without adding product value.

## ADR-012 — Canonical records over derived or duplicated browser business state

**Decision:** Supabase canonical records are the source of truth for clients, bookings, payments and settings. Admin client lists come from canonical client data, not reconstruction from booking history. Browser storage and React state may hold temporary UI/draft/cache state only and must not become an alternative business database.

**Reason:** V1 represented booking/client data in database columns, JSON notes, React state and browser storage at the same time. The resulting contradictions and stale compatibility layers were a major reliability problem.

## ADR-013 — Maintainability changes must target ownership, not cosmetic file splitting

**Decision:** V2 will use feature-scoped components, styles and modules, but file splitting alone is not treated as a performance optimization. Performance work focuses on bounded queries, reduced duplicate work, lazy loading and smaller active bundles. Dead or permanently disabled code is removed rather than hidden.

**Reason:** V1's very large App/Admin/CSS files made regression risk high, while some runtime cost came from data-loading and repeated calculations rather than file size itself.


## ADR-014 — One visit, separate session rows

**Decision:** A booking represents one visit to one address and start time. Each person's treatment is stored as a separate `booking_sessions` row. The booking stores the summed treatment duration, while pricing and session identity remain per session.

**Reason:** This preserves the V1 client experience while permanently preventing the old `2 × 60 = 1 × 120` modelling error. It also keeps travel buffer around the visit rather than between sessions inside the same visit.

## ADR-015 — Payment has one authoritative record per booking

**Decision:** V2 uses one authoritative booking-payment record linked one-to-one with the booking. Booking status and payment status remain separate state machines; payment state is not duplicated in a second order authority and booking JSON notes.

**Reason:** V1 could disagree across order state, booking state and notes. A single payment authority makes verification, cash approval, cancellation and refund history explicit.

## ADR-016 — Calendar blocking uses one canonical block model

**Decision:** Date-specific unavailable time and Admin personal events use one canonical calendar-block model with a type/kind field and optional personal-event presentation metadata.

**Reason:** Both concepts block availability. A single scheduling-block source simplifies availability queries while still allowing Admin to distinguish blocked time from named personal events.

## ADR-017 — Client draft, finalization and payment reference (2026-09-27)

**Decision:** Keep unfinished booking inputs and an in-flight finalization request in versioned session storage; keep only the opaque hold client key in local storage. An ambiguous transport failure locks the request for retry using the identical payload and idempotency key. Store only the returned booking ID for subsequent authenticated server reads, not a browser booking database.

**Reason:** Reloads and authentication redirects must preserve the draft without creating duplicate bookings. Confirmation requires a successful finalization result or an authenticated read of the canonical booking.

**Decision:** Public bank details use explicit `VITE_BANK_*` configuration, matching V1's configuration approach. Finalization supplies the payment reference; the UI does not invent it before booking creation. Bank-transfer submission remains awaiting verification, and cash remains awaiting approval. No notification-delivery claims are made from the browser.

**Reason:** The deployed V2 finalization contract returns the reference only after the atomic transaction. A client-side reference or preliminary order would restore the V1 architecture defect. Missing bank configuration is visible and prevents bank-transfer submission.

## ADR-018 — Status changes are guarded and recorded in the database (2026-10-09)

**Decision:** `bookings.booking_status` and `booking_payments.status` may only move along the allowed transitions defined in `20261009100000_booking_status_guard_and_audit.sql` (for example `cancelled`, `completed` and `no_show` are final, and cash must be approved before it is paid). Every booking or payment creation and status change is recorded in the append-only `booking_status_events` table with the acting user, actor type and role. Admins can read the history; nobody can edit or delete it.

**Reason:** Browser roles already cannot write these tables, but SECURITY DEFINER commands, the service role and manual SQL could still make an impossible change with no record. Tests and fixtures must now reach a state by a legal path or by inserting rows in that state. History starts at this migration and is not backfilled.

## ADR-019 — Bookings waiting for payment are decided by the Admin, never by a timer (2026-10-10)

**Decision:** Nothing is cancelled automatically. A bank-transfer or cash booking that is waiting for payment keeps its time until the Admin confirms the payment or removes the booking. Removal (`admin_remove_pending_booking`) records the booking as cancelled by the Admin and rejects its payment record; nothing is deleted and no fee is implied. The Admin may also confirm a transfer the client never declared, and the Payment Review list shows every booking that is waiting, with when it was booked. Clients are limited only by the existing active-booking limit (one for a new client, five for a returning client). Clients cannot list or hold times more than 40 days ahead and need two hours' notice; Admin booking has no horizon.

**Reason:** The business is built on loyalty and personal follow-up. A client who pays late must not lose their time or be double-booked, and the Admin decides when a booking will not be paid or attended. `bookings.payment_reservation_expires_at` is kept for history but is deprecated and always null. Automatic expiry or reminders could be added later as an explicit change.

## ADR-020 — First-use scope, build order and operating choices (2026-10-10)

**Decision (owner's answers):**
- **First use:** the owner alone enters her own bookings first; clients are opened up later. Start using the app as soon as the daily core works, and add the rest while using it.
- **Build order:** (1) daily core: finish Admin New Booking; confirm/cancel/reschedule/complete/no-show with recorded reasons and history; Agenda/Today; client self-cancel and reschedule; (2) alerts; (3) schedule control (working hours, days off, overrides, block time and personal events); (4) clients (search, profile, addresses, notes/preferences, history); (5) settings screens for services, prices, areas, bank details and booking/cancellation rules, because she wants to change everything herself and not through the database; (6) waitlist. Quick contact actions (call, WhatsApp, directions) come with the daily core. Analytics, receipts, finance, diagnostics and the WhatsApp assistant stay out of scope for now.
- **Alerts:** Telegram, email and in-app for new bookings and "I've paid" claims, each with a link to the exact booking, sent from committed events (outbox). Telegram reuses the existing bot (token entered by the owner as a secret, never committed). Email uses Resend from an address on vadmassage.com (DNS records needed).
- **Client changes:** clients cancel and reschedule themselves. Inside 24 hours it is still allowed online, but the full appointment fee is recorded as due (the Admin can reduce or waive it). A booking can be cancelled free within one hour of being made. Fees are recorded; money is collected outside the app.
- **Accounts:** unchanged (sign in with email or Google as part of booking), which self-service needs.
- **Hosting and data:** booking.vadmassage.com on Vercel; start fresh with no import from V1. Test mostly on iPhone Safari, then Android Chrome.

**Reason:** Keeps the launch to what is needed to run the diary, in an order that lets real use find problems early. Supersedes the open question in ADR-019 about reminders: alerts are in scope, automatic cancellation is not.

## ADR-021 — Booking lifecycle: late fees, refunds and how changes are made (2026-10-10)

**Decision:** The Admin completes, no-shows, cancels and reschedules bookings only through retry-safe commands (`admin_complete_booking`, `admin_mark_no_show`, `admin_cancel_booking`, `admin_reschedule_booking`, `admin_settle_late_fee`, `admin_record_refund`), each recorded in the status or schedule history.
- A cancellation or change is free more than 24 hours before the appointment and free for one hour after the booking was made, even for a same-day appointment. Exactly 24 hours before is not "more than 24 hours", so it is charged.
- Inside 24 hours a client-requested cancellation or change is still allowed. The full appointment price is recorded as a late fee due; the Admin may set any amount from zero to the full price (zero waives it, and the standard amount stays on record). A change the Admin makes on her own account never charges the client. A second late change does not add a second fee.
- A no-show records the full price as due unless the Admin chooses a lower amount.
- Money is collected outside the app. If a paid booking is cancelled, the fee is kept from the payment and the balance is recorded as a refund due until the Admin records it as sent.
- Rescheduling uses the same availability engine as booking, ignoring the booking being moved; the Admin cannot place a booking in a time the engine would refuse. Admin booking has no 40-day horizon (a 365-day sanity limit remains).
- The fee rule lives only in the database (`late_fee_standard_gbp`); screens ask `admin_late_fee_preview` and never repeat it.

**Reason:** These are the owner's answers (ADR-020 and follow-up): clients should not have to message her for routine changes, loyal clients are treated kindly, and every money-affecting outcome is visible and reversible by her decision. Client self-service cancel and reschedule will call the same rule and engine.

## ADR-022 — Clients manage their own bookings at /account (2026-10-11)

**Decision:** A signed-in client (including a guest on the same device) sees their bookings at `/account` and can cancel or change the time without messaging the Admin. The page asks the database for everything it shows: the terms (`get_my_change_terms`), the times (`get_my_booking_availability`), and the result (`client_cancel_booking`, `client_reschedule_booking`). Inside 24 hours the change is allowed, but the client must tick that they understand the exact late fee; the command sends that fee back, and if it no longer matches (the 24-hour mark passed while the page was open) it refuses and the client reviews again. Changes use the client booking rules: two hours' notice, 40 days ahead, the same availability engine. Errors shown to clients are a fixed set of kind sentences; technical messages are replaced.

**Reason:** The owner wants routine changes to happen without a message to her, with the fee rule applied consistently and visibly. The Admin is told through the same event stream as other changes (`booking.cancelled` and `booking.rescheduled` carry `initiated_by: client`).

## ADR-023 — Alerts are written by the database and delivered by a small sender (2026-10-11)

**Decision:** When a booking event is committed, the database writes the finished message (title, text, link to the exact record) into `notification_deliveries` for three destinations: an in-app alert for the Admin, a Telegram message and an email to her, and where relevant an email to the client. In-app alerts need nothing outside the database. `api/dispatch-notifications.js` delivers the Telegram and email rows, records success or failure, and retries failures after 2, 8, 18 and 32 minutes (five attempts). It runs only for a caller who holds `CRON_SECRET` and uses the server-side service key, which is never in the browser or repository. The Admin is alerted about new online bookings, "I've paid", cash requests and client cancellations or moves, never about her own actions. Clients are emailed when a booking is confirmed, cancelled, moved or refunded.

**Reason:** One tested place owns the wording and the rules for who hears what, so Telegram, email and the app never disagree. The in-app list works even if Telegram or email is down. A narrow, secret-protected sender keeps the powerful key off the client and makes delivery failures visible rather than silent. Setup steps that need the owner's accounts are in `docs/NOTIFICATIONS_SETUP.md`.

## ADR-024 — The Admin edits her own schedule, with warnings instead of silent clashes (2026-10-11)

**Decision:** Working hours (usual week), special days (days off or different hours for one date) and blocked time or personal events are edited from the Admin app, directly in their tables, which already allow only the Admin and enforce valid times. Before saving a day off, shorter hours or a block, the screen asks `admin_schedule_conflicts` which live bookings (pending or confirmed, including their travel allowance) it would clash with, shows them by name, and lets her save anyway. Existing appointments are never moved or cancelled automatically. Times are chosen in 30-minute steps to match the availability engine, and the start-and-end rules are checked on screen with plain sentences before the database checks them again. Blocks make the time unavailable for treatment and for the travel around it (the availability engine already treats blocks that way).

**Reason:** She wants to change her hours, take days off and block personal time without touching the database. A warning that names the booking is safer than refusing the change, because a day off or a dentist visit may be unavoidable, and safer than silently leaving a booking in an impossible slot.

## ADR-025 — The Admin manages clients from a directory and profile (2026-10-11)

**Decision:** `/admin/clients` searches the canonical client records (the existing bounded search: 20 best matches) and adds new clients with an address. A client's profile shows contact links, a summary (visits, money paid, upcoming, last visit, next appointment, late fees and refunds still due, all computed by `admin_client_summary` on the server), editable details, saved addresses (add, change, make default, remove), private notes, booking history (loaded in pages of 15), and a switch for online booking. "New booking" from a profile opens the booking wizard with that client already chosen. Editing a client goes through `admin_update_client`, which refuses an email or phone another client already uses, so records cannot silently duplicate. A client's record, their login account and their bookings stay separate things: editing contact details does not change a login, and removing an address never changes a past booking, which keeps its own copy.

**Reason:** The owner needs to look someone up, see what they owe and when they last came, and correct details without the database. Keeping the contact fields behind one checked command prevents duplicate clients, and keeping money and visit totals on the server avoids loading a whole booking history to add up a number.

## ADR-026 — Services, prices, areas, extras and bank details are edited in the app (2026-10-11)

**Decision:** The Admin edits treatments (with the three lengths and their prices), extras, and areas (travel surcharge and congestion charge) from More. She can add, change, hide or show, and reorder them. Prices and fees apply to new bookings only; existing bookings keep the price they were booked at (they store their own copy). Hiding an item removes it from what clients can choose but keeps it for history. A shown treatment must offer at least one length. New items get a plain web-safe name derived from their name, kept unique. Bank details are saved through `admin_save_bank_details` (name, optional bank, six-digit sort code, eight-digit account number, optional note) into the Admin-only `business_settings` table. Clients receive them only through `get_bank_details()`, and only when they hold a client record (guests included). The build-time `VITE_BANK_*` values remain as a fallback for when nothing is saved.

**Reason:** She wants to change her prices, areas and bank details without touching the database or redeploying. Keeping bank details out of a public table and behind a function that answers only signed-in clients limits who can see them, and the fallback keeps current behaviour working until she has entered her own.

## ADR-027 — The booking rules are settings the Admin can change (2026-10-11)

**Decision:** Six rules live in `business_settings` and are edited at More, Booking rules: how many days ahead clients can book (40), hours of notice (2), free-cancellation window (24 hours), grace period after booking (60 minutes), and how many upcoming bookings a new client (1) or returning client (5) may hold. The booking, availability, reschedule and fee functions read them through `business_setting_int`, which falls back to the default if a value is missing or unusable, so a bad setting can never break booking. A rule applies from the moment it is saved to anything done afterwards; bookings already made and fees already recorded are not recalculated. Notice is now an exact time comparison (the appointment must start at least that long from now, across midnight), so a notice longer than the rest of today works correctly. The booking pages read the few public numbers they need (days ahead, notice, free window, grace) from `get_booking_rules()` so the date picker limit and the wording ("up to 24 hours before…") follow the settings. Admin booking is not limited by the horizon or notice. Ranges are enforced by the database and checked on screen first.

**Reason:** The owner wants to change these rules herself without a developer. Keeping every use of a number behind one reader means the wording, the limits and the fees cannot drift apart.

## ADR-028 — A simple waitlist that never books by itself (2026-10-11)

**Decision:** When the day a client chooses has no suitable times, the booking page offers to take their name, phone or email, a time of day (any, morning, afternoon or evening), the treatment length and an optional note. Anyone may do this without signing in (they are choosing a date before sign-in); a request is limited per phone number or email (three open requests), overall (300 open), and the same person asking twice for the same day and length is one request. The Admin sees open requests at More, Waitlist, soonest day first, each with the times that could be booked for that person right now (computed by the same availability engine as booking, inside their preferred time of day), quick call, WhatsApp and email links, and a private note. She can record that she offered a time, mark it not answered, close it as booked or no longer needed, and book for a client straight from the request when they already have a client record. She is alerted (in the app, Telegram and email) when someone joins and when a booking is cancelled or removed on a day people are waiting for. Nothing is ever booked, offered or messaged to the client automatically.

**Reason:** The owner asked for a waitlist but a workable one. Anyone's contact is taken only when there is genuinely nothing free, matching the real availability rules shows her at a glance who she can help, and keeping every offer and booking in her hands matches how she works with clients.

## ADR-029 — Design polish: the brand's type, one set of colours, and a calmer progress line (2026-10-11)

**Decision:** Headings use Playfair Display and interface text uses Inter (loaded from Google Fonts with a Georgia and system-font fallback), as the brand calls for. Every colour used by the app's stylesheets is now a named value in `src/index.css` (`--ink`, `--green`, `--gold`, `--danger` and so on), so the look can be changed in one place. On a phone the eight-step list in the booking flow becomes one line ("Step 4 of 8 · Date & Time") and a thin progress bar; the full list stays for screen readers and for wider screens. The brand mark is a small monogram instead of plain letters. The tab icon, title and description are VadMassage's own rather than the project template's. Buttons give a small response to touch and hover, and all motion is switched off for people who ask for reduced motion. Admin page titles use the heading face. Unused template leftovers (`App.css`, three sample images) were removed because nothing imports them.

**Reason:** The first impression for a client should feel warm and personal, and the screens should look like one product. Fonts from Google send visitors' addresses to Google; if that is not acceptable they can be served from the site itself instead (noted in `GO_LIVE_CHECKLIST.md`).

## ADR-030 — Repeating bookings are a standing rule, not a year of bookings (2026-10-08, built 2026-10-09)

**Decision:** A repeating booking is stored as one standing rule (weekday, time, length, area, address, start date, optional end date). The rule keeps that weekly slot free in the availability search until it ends; skipped dates are released. Only the next one or two sessions exist as real bookings, and the app creates the next one when the previous is completed or cancelled. Only the next booking asks for payment; the client is reminded 7 days before the following session (the number of days is a setting). Nothing is cancelled automatically: an unpaid session is shown to the Admin as overdue and she decides. Cancelling one session skips that date and the repeat carries on, under the usual 24-hour fee rule; the one-hour free-cancel grace does not apply to sessions the app creates itself. A new price applies from the next session created, and the client is told. The Admin creates repeats from a client's profile first; a client-facing "repeat weekly" option comes later. The client booking horizon is raised from 40 days towards a year through the existing setting.

**Reason:** Some regulars book the same weekday every week. A year of real unpaid bookings would crowd the Review screen and block slots if a client drifted away, while a standing rule keeps their slot safe without that clutter. Building the Admin side first lets her get the rules right with clients she already knows.

**How it was built:** `booking_series` holds the rule and `booking_series_skips` the dates that are not booked (skipped, cancelled, moved, or a clash). The held slot is a `calendar_blocks` row of kind `series_hold`, so the availability search and clash checks needed no change. The first booking is made with the repeat through `admin_create_series`, which calls the same `admin_create_booking` command as a new booking. `run_series_maintenance` (called by the sender endpoint, at least daily) tops up the holds and makes each booking when its date is inside the reminder window (`series_payment_reminder_days`, 7 by default, editable in More, Booking rules). It acts as the Admin who made the repeat so the same availability, price and snapshot rules apply. If a time is no longer free the date is skipped and the Admin is alerted instead of anything being forced. The client sees the usual booking page; the booking is announced by a "time to pay" message instead of the ordinary "booked" one. Not built yet: a client-facing "repeat weekly" option, and clients skipping a date from `/account`.

## ADR-031 — Blocked time runs over a range of dates and hours (2026-10-09)

**Decision:** Blocking time takes a start date and time and an end date and time, like an event in a phone calendar, so one block can be a holiday, a few days, "Friday 14:00 to Monday 09:00" or two hours in a day. Each day keeps its own row in `calendar_blocks`, so the availability search, the calendar and the clash check work as they did; rows that belong to one block share a `group_id` and are saved, changed and removed together by `admin_save_block_range` (one command, so a block is never half saved). The clash check, `admin_block_range_conflicts`, lists every live booking the range covers, day by day, and nothing is moved or cancelled for her. A block can cover up to a year. Blocked time can be added, changed and removed from the Calendar and from More, Working hours, Special days, where upcoming blocks are listed. Special days (a day off or different hours for one date) stay as they were.

**Reason:** She wanted to block more than one day, or only some hours, without adding each day by hand. Splitting a block into one row per day keeps every existing rule that reads blocks correct, instead of teaching each of them about ranges.

## ADR-032 — One design language and shorter journeys, for clients and for the Admin (2026-10-12)

**Decision:** Both sides now share one set of building blocks (`src/index.css` tokens, `src/ui.css`). Colour says whose turn it is: amber means it needs the Admin, a dashed outline means the client's turn, green is settled, grey is finished or cancelled, plum is a no-show and red is a late fee. Every screen has one filled button for the next step, outlined buttons for the rest, quiet text for going back, and a red outline (filled only inside a confirmation) for anything destructive. Headings use Playfair Display with lining numerals and, on the client side, one italic gold phrase; everything else is Inter.

For the Admin: a bottom tab bar on a phone (a rail on a wide screen) with badges for what needs her, a "Needs you" strip at the top of the Agenda with Verify and Approve one tap and one confirmation away, toasts that say what just happened, loading shapes instead of the word "Loading", and Alerts grouped by booking. New booking is one numbered page where treatment and length are tapped, the time comes from the same picker clients use, and the client's usual choices are already filled in.

For clients: choosing a length goes straight on to choosing a time; the time page opens on the first day with room and shows the full days before it; looking at other days never lets go of a time that is held; the review is a ticket with preferences behind one optional section and a price that follows the choices without a button; "Continue as guest" is the plain way on and signing in waits behind "Returning client?". A confirmed appointment can be added to a calendar, a regular client is offered their usual booking, links such as `/?area=chelsea&treatment=massage&minutes=60` open the booking part-way through, and moving an appointment uses the same day-and-time picker.

**Reason:** The owner asked for fewer clicks and scrolls, more defaults, clearer typography and an app that feels modern from both ends. Doing it as one design language keeps the two sides looking like one product and keeps every later screen cheap to build. Nothing about the rules changed: availability and travel buffers, the cancellation window and fees, the payment rules (a transfer is never marked paid by the client; cash needs a deliberate confirmation), the order of the booking steps and the three lengths are as they were, and there are no database changes in this work.

**Added later the same day:** The Agenda, the Day view, To check and Alerts keep what is on screen while they are read again, and read again whenever the Admin comes back to the app (a home-screen app has no pull to refresh). The Agenda re-reads whatever months are on show a month at a time, because one read is limited to 31 days. Cancelling offers No fee, Standard fee and Full price in one tap, and moving an appointment uses the shared day-and-time picker; both keep their buttons in reach while the form scrolls, as does Block time. Appointment cards put the treatment and the postcode on one line. On the booking page the areas come before the three steps, and on the payment screen the terms sit right under the bank details; the main button is always pressable and, if the terms are not ticked yet, takes her to the box and says why (a greyed button gave no reason). Nothing about when a booking counts as paid changed: the client's button only reports that they have made the transfer.

**After an independent review and a tester using the app on a phone:** a cancellation never goes ahead on a fee the Admin has not seen (the standard fee only fills in a fee she has not chosen, and if it cannot be looked up she chooses one); a refresh that fails just after the phone wakes is tried once more, quietly, before anything is said; a reserved booking has no way back, so the payment screen says so and offers "Change the time or cancel this booking" (the account page); a phone number or postcode that cannot be right is named beside its field before a time is reserved; and a second tap that lands just after a screen has changed is ignored for 0.4 seconds, so it cannot choose the next treatment or length by accident. The "New test client" testing helper is limited to development builds, so it can no longer be reached on the live page with `?test=1`. Every appointment still to come has a Directions button beside its status (Google Maps, the same link as in the booking details), as a control of its own next to the card, never inside it. Tests that place a booking relative to the clock were made safe at any time of day. Still open on purpose: the client's page counts an appointment earlier today as upcoming, and guests who book twice appear twice under Clients (a guest's email is never trusted to link them to an existing client).

**How it was built:** `DayTimePicker.jsx` is the one picker (booking, moving an appointment, Admin New booking). The booking store gained `selectSlot(start, date)` (the viewed day is saved only with a chosen time) and `refreshQuote` (the price updates without locking the screen, and a price for choices that have since changed is dropped). Small pure modules carry the logic that can be tested without a browser: `timeOfDay`, `dateStrip`, `usualBooking`, `deepLink`, `calendarFile` and `groupAlerts`.

## ADR-033 — Two profiles that might be one person are combined only when the Admin says so (2026-10-13)

**Decision:** Someone who booked as a guest and later registers with the same email now gets a profile of their own instead of an error, and the app never combines profiles by itself. The database notices profiles that share an email or a phone number (a phone number is compared by its last ten digits, so 07700 900123 and +44 7700 900123 match). All such pairs are listed in a "Might be the same person" note at the top of the Clients page, and every client's page has "Combine with another client…" for pairs the app cannot spot. When a pair has something to combine (a booking on either profile), the Admin is also told once in the app: "Is this the same person?". She sees the two profiles side by side and answers: combine them, "No, different people" (remembered, so she is never asked about that pair again) or decide later. Combining asks once more, because there is no undo button.

Two profiles that each have their own login are never offered and can never be combined. Where one profile has a login, that one stays. Where neither has, she chooses; the suggestion is the one she added herself rather than a guest, then the one with more bookings, then the older. A guest's profile can be reached from the browser that made it, and nothing proves who is behind it, so it is never suggested over one the Admin added. Where a mistake is easier to make the screen says so and "Yes" is no louder than "No": the first names differ, or only a phone number matches (a phone number typed when booking is never checked, an email that has been confirmed is). When a guest's profile goes, the confirmation says the guest will then see and change those bookings only by signing in.

The profile that goes hands everything to the one that stays: its bookings (status, payment, fees and the address each was made for are untouched), repeat bookings, notes, addresses, waitlist requests and any time still held. A repeat keeps a copy of the booking it makes each week, which names the client and perhaps a saved address; both follow the move, or the daily job could not make the next session. An address the other profile already has is not copied twice, but only when their entry instructions agree or one has none; what the copy knew (instructions, a label) is kept on the original, and the whole copy is saved in the history. The profile that stays also gains an email, phone number or last name it lacked, the earlier "client since" date, and keeps online booking switched off if it was off on either. A private note on it says what was combined, and the profile that went is saved whole in `client_merges`, so a mistake can be put right by hand.

**Reason:** A guest's email has never been checked, so using it to link a guest to an existing profile would hand that person someone else's bookings and addresses if the email was mistyped or borrowed; and refusing the registration (the old behaviour) left a real client stuck with a message they could not act on. The Admin is the one person who can tell whether two entries are one client, it takes her a few seconds, and it only happens when the app sees a likely match.

**How it was built:** Migration `20261022100000_same_person_clients.sql`. `activate_my_client_account` now ignores profiles that belong to a guest session when it checks whether an email is already taken (a different real login on the email still blocks, as before). `client_duplicate_pairs` finds pairs by lookup (an index on the phone key as well as on the email), so saving a profile stays quick with thousands of clients. A trigger on `clients` raises `client.possible_duplicate` when a profile is saved with an email or phone, but only one new question per save, only about a pair with a booking on either side, and never twice about a pair, so nobody can flood the Alerts page by making many profiles with one email; every pair still shows on the Clients page. The alert is written by `plan_client_notifications`: it says what matched and does not claim when anything happened, and it is in the app only, because nothing about it is urgent. `client_not_same` holds her "different people" answers and `client_merges` the history of every combine (the whole profile that went, which rows moved, who did it and when; readable by the Admin only). Four Admin commands do the work: `admin_possible_duplicates`, `admin_combine_preview`, `admin_keep_clients_separate` and `admin_merge_clients`. The last is one command, all or nothing, and safe to repeat: the same request key returns the same answer. It takes the same email lock as registration and locks a repeat before its client, as the repeat job does. Because people she calls "different" will often share an email or phone, `admin_update_client` now checks only a value that is being changed (it used to refuse any save while another profile shared the email or phone, so such a pair could not even have a name corrected). The screens are `CombineClients.jsx` (route `/admin/clients/combine?a=…&b=…`, which is also where the alert opens), `PossibleDuplicates.jsx` and `CombinePicker.jsx`; an alert may open only pages inside the Admin (`adminPageFromLink`; the old check ignored digits, so the repeat-clash alert's link to a client never opened).

**Found by an independent review and fixed before release:** the weekly repeat's stored copy still named the old profile, so after a combine the daily job would have failed every week, released the slot and sent false "no longer free" alerts; a copy of an address could carry entry instructions that were then lost; the check for matches read every client on every save (4 seconds at 8,000 clients; now milliseconds); anyone could raise many alerts with many guest profiles; and a guest could be suggested as the profile to keep.

**Limits, on purpose:** A guest who comes back on a new phone or browser makes a new guest profile each time; each one is combined by hand. Pairs that already exist when the change is applied are listed on the Clients page but raise no alert until one of the two is next saved. A registration can book online until the Admin combines it with a profile she had switched off, because nothing links them before she says so. `client_merges` keeps the removed profile's name, email and phone; if a client's data is ever to be erased, those rows go too. There is no Telegram message or email for this alert. The database change was applied to the online Supabase project on 2026-10-13 with the owner's say-so (before that, the preview of the screens showed a plain error when she tried to combine two profiles, as expected); on a project without it the Clients note stays hidden and the combine screen shows a plain error.

## ADR-034 — A receipt is made from a paid booking, kept as it was, and sent with the tools already there (2026-10-13)

**Decision:** Receipts were out of scope in ADR-020; the owner has now asked for them so she can send one to a client who asks after a booking. A booking whose payment has been marked as received shows a "Receipt" button on its page. Opening it the first time makes the receipt and gives it the next number (`VM-2026-0001`, `0002`, and so on, with no gaps; the year is the London year and the numbers start again each January); opening it again shows the same one. It carries her business name and contact details (and an address only if she saved one), who it is for and the booking reference, the appointment (day, time and length), one line for each treatment, extra, travel charge and congestion charge, the total paid, how and when it was paid, and an optional note and closing line. It never shows the client's treatment address, says nothing about VAT (she is not VAT-registered, and it is not a VAT invoice) and says nothing about card payments. She sends it by email (from the app, text only, no PDF), by WhatsApp (a link that opens the client's chat with the receipt already typed in) or through the phone's share sheet, which copies the text on a computer.

A receipt can only be made for a confirmed or completed booking whose payment is marked as received for exactly the booking's total. It is refused, in plain words, for a booking still waiting for payment, a cancelled booking (even if a late fee was kept), a missed appointment and a refunded payment. If the treatment lines on the booking do not add up to its total, the booking's own subtotals (treatment, extras, travel, congestion) are used instead; if neither adds up, no receipt is made rather than a wrong one. Her business details are saved once (More, Receipt details) and are needed before the first receipt.

A receipt is kept as it was on the day it was made: a later change to a price, a name or her own details never alters it. **Edit** corrects the words on that one receipt: who it is for, a note, the words of each line, and her details. The amounts, the receipt number, and how and when it was paid are never editable, because they must match the money received (the payment date is the day she marked the payment as received). Every earlier version is kept (`booking_receipt_revisions`). If the appointment is moved after the receipt was made, the receipt says so and "Update the date and time" copies the new date and time from the booking; a booking whose price no longer matches the receipt is flagged but cannot be edited from here (nothing in the app changes a price after payment).

The email uses the same queue and sender as every other email (ADR-023). The receipt reports only what is known about the newest email of it: waiting for the sender, sent, not through yet and trying again by itself, or given up after five tries. "Emailed" is never shown for an email that is only queued. The screen holds the request key of an email that was asked for but not confirmed, so pressing Email again after the connection dropped can never send it twice; once an answer arrives, or the receipt is changed, the next press is a new email. After an edit, a line says the email already sent has the old words. An email still waiting after ten minutes is shown as "still waiting to be sent", with no promise of a quick send (the sender may not be running); one that was cut off on its last try is shown as failed, and one whose delivery record is gone is never called sent.

A receipt cannot be sent or changed once its booking has been cancelled or marked as missed, or its payment refunded, even from a screen that was already open (the database refuses). A receipt email that is still waiting to go, or waiting to be tried again, is stopped at that moment, so the sender never delivers "Total paid" for money that was handed back; an email already being handed to the mail service at that very instant cannot be stopped. The booking page then shows a note that a receipt was made, and whether it was emailed.

**Reason:** She asked for a receipt she can send. Keeping it as a record of money received makes the simple rules possible: nothing on it can disagree with the booking's payment, the numbering has no gaps, and the same words go to the email and to the message she shares. No PDF, address or VAT, because she said she does not need them.

**How it was built:** Migration `20261023100000_booking_receipts.sql`. `booking_receipts` (one per booking, the frozen content, who made it and when, when it was emailed and last edited), `booking_receipt_revisions` and `receipt_counters` have row security on and no direct access for anyone; everything goes through Admin commands (definers with an empty search path, closed to anonymous and guest sessions): `admin_receipt_details` and `admin_save_receipt_details`, `admin_issue_receipt`, `admin_get_receipt` (looks without making one), `admin_edit_receipt` and `admin_email_receipt`. Internal helpers (`build_receipt_snapshot`, `receipt_refusal`, `receipt_message`, `receipt_json`, `receipt_clean_text`, `receipt_check_business`) cannot be called from outside. `receipt_message` is the one place the words are written, used by the email and by the share text. Opening, editing and emailing one receipt queue up behind the same per-day lock the cancel, move, no-show, refund and payment commands use, and then behind each other for that booking, so a receipt is never made, changed or sent from a booking that is being cancelled at that moment, and a double tap cannot make two receipts or use up a number. Two triggers (`stop_receipt_emails`, on a booking becoming cancelled or missed and on a payment leaving "paid") stop a receipt email that has not gone yet. The email is a normal client delivery (`booking.receipt_emailed`, deduplicated by the request key) with the title "Your receipt from <business> (<number>)"; making and editing a receipt are recorded too. Text is tidied: every kind of line break (including the separator some phones type) becomes a plain one, and in a one-line field a space; control characters and the ones that flip the direction of text are refused; marks that cannot be seen (zero-width space, direction marks, the byte order mark) are dropped; and the word the sender swaps for a web address ("{link}") is taken out until none is left, so it cannot be rebuilt from pieces. The same tidying is applied to text that comes from elsewhere (the client's name, the treatment, extra and area names on the lines, the greeting), and a name longer than 120 characters on a receipt is cut to fit. The screens are `ReceiptPanel.jsx` (the receipt, Edit, sending, and `ReceiptNote` for a cancelled booking), `SettingsReceipts.jsx`, `receiptsApi.js` and `receiptState.js` (what may be said about an email).

**Found by an independent review and fixed before release:** a receipt could be emailed or edited after its booking was cancelled or its payment refunded, because only the screen hid the button; the screen said "Emailed" the moment an email was queued, even if it later failed; a dropped connection followed by a second press could send two emails; a receipt kept the old date after its booking was moved, with no warning; a missed appointment could be given a receipt; and odd characters, an over-long name and the sender's link word were not handled.

**A second independent review, of the fixes, found and I fixed:** a receipt email still waiting to be sent would have gone out after the booking was cancelled or refunded (it is now stopped); the lock described above was only for one receipt and not shared with the cancel and refund commands (it now is, and a test proves the day lock is taken); a request key kept after a dropped connection could swallow a later, deliberate resend (it is now forgotten once the receipt has been read again); "it is sent within a minute" was a promise nothing kept (it now says it usually goes within a few minutes, and says it is still waiting after ten); a receipt whose delivery record was gone was called emailed; the link word could be rebuilt from nested pieces, a line separator passed the one-line rule, and names on the lines were not tidied; focus was lost when leaving a booking for the receipt details. Several tests could not fail (a check that every Admin command has an empty search path passed for one that had none, an address check looked at a key that never exists, a count of used numbers counted nothing) and are repaired; tests were added for a cancel, refund or missed appointment after a receipt, two presses at the same moment, a second year's numbering, two sessions, odd text, and every command refusing a guest.

**Limits, on purpose:** A cancelled booking has no receipt even where a late fee was kept, and neither has a missed appointment; say so if that should change. Two people changing one receipt at the same moment: the last save wins, and the earlier version stays in its history. The history is protected by having no direct access, not by a database lock against deletion; a booking that has a receipt cannot be deleted until its receipt is (on purpose, as a money record), so test data is cleared in this order: `booking_receipt_revisions`, `booking_receipts`, then `receipt_counters` (to start the numbering again), then the bookings. Receipts made while trying the app out use up numbers; clear them before real clients start (see the go-live notes). The number is given when she first opens a receipt, not when payment is received. Email delivery depends on the same sender settings as other emails and has not been tried with the real provider. An email already being handed to the mail service when the booking is cancelled cannot be stopped. Esc closes the whole booking window, as it does for every form in it, and loses a half-typed Edit. The database change was applied to the online Supabase project on 2026-10-13 with the owner's say-so (that one file, after a dry run) and checked there read-only; until then the receipt screens showed a plain error on a preview.

## ADR-035 — The Admin can choose any time for a new booking, but never a double booking (2026-10-13)

**Decision:** The New booking page still offers only the usual times: a day's appointments are kept in one run with a 60 minute gap between them, inside working hours (so on a day worked 14:30 to 17:30 with 14:30 to 15:30 booked, only 16:30 is offered). Under them the Admin has a **Show all times** button. It lists every half hour of the day, from 06:00 to the last start that finishes by midnight. The usual times look as before; the others are dashed, and choosing one says in plain words what she is setting aside: a shorter gap than her usual 60 minutes, the time being outside her working hours or on a day off, or falling in blocked time or a personal event. The same note is repeated beside the price. A time that would overlap another appointment, or one a client is in the middle of booking, is greyed and cannot be chosen; tapping it says what it clashes with. Also refused, by the database: a time that has already begun, one that would run past midnight, and one more than a year ahead. While a client is part-way through booking that day (a time is held for them for a few minutes), unusual times are paused as well: the database refuses them and the screen says so, because an unusual appointment elsewhere that day could take away the held time (a held time is only confirmed if it is still a usual time when the client presses Confirm). Otherwise it is an ordinary confirmed booking with the usual 60 minute travel allowance recorded. A repeating booking is only offered at usual times (the weekly bookings that follow are made at usual times only), so choosing an unusual time switches the repeat off.

**Reason:** She knows more than the rules do: a shorter gap when two clients live next door, a longer day, an evening. Keeping the rules as the default and showing every time with the reason for each makes setting one aside a deliberate act, and refusing a double booking prevents the one mistake that cannot be undone from happening by accident.

**How it was built:** Migration `20261024100000_admin_any_time.sql`. `admin_booking_times(date, minutes)` (Admin only) returns her working hours that day, what is booked (and held by a client who is booking), blocked time, and every start with two facts: whether it is a usual time (exactly the times `admin_booking_availability` offers) and whether it overlaps another appointment or a held time (`admin_time_clash`, an inside helper shared with the booking command). `admin_create_booking` accepts an optional `any_time` (yes or no; anything else is refused). With it only the checks above remain; without it nothing changes. `admin_create_series` refuses `any_time`. The wording of what is being set aside is written by the screen (`times.js`) from what the database reports. The shared day and time picker gained an optional footer for the button; the client booking page and moving a booking do not use it. The database change was applied to the online Supabase project on 2026-10-13 with the owner's say-so (that one file, after a dry run) and checked there read-only.

**One change to the shared availability engine, found while building this:** `compute_booking_availability` works out the times offered from the first and last appointment of the day. Each of the two candidate times was checked against only one end of the working window: the time before the first appointment against opening time but not closing time, and the time after the last against closing time but not opening time. That never mattered while every appointment lay inside working hours. With any-time bookings it would have let an appointment at 06:00 offer clients 08:00, before a day that starts at 10:00. Both ends are now checked for both. A day on which every appointment is inside working hours is offered exactly the times it was before (the existing availability tests are unchanged and pass), and tests prove the loophole is closed, including through the call the public booking page makes.

**Limits, on purpose:** Starts stay on the half hour. Moving an existing appointment (Reschedule) still offers the usual times only. After an unusual booking, the rest of that day is usually closed to clients, because the first and last appointments of the day bound what is offered. The app does not warn about the gap between two appointments that were both set aside on purpose. A repeating client's weekly booking is made at a usual time only, so an unusual booking on a day when a repeating client's time is kept free may stop that week's repeat; the screen warns when that day has one. The sticky Create booking bar covers whatever is under it while scrolling, as it always did, so an accessibility checker can flag a time under it at one scroll position (reaching a time by keyboard keeps it clear of the bar).

## ADR-036 — A client with no bookings can be deleted; a client with bookings cannot (2026-10-13)

**Decision:** At the bottom of a client's page, **Delete this client…** removes someone added by mistake, a profile made twice, or a made-up test profile. It is offered only when the client has no bookings and no weekly repeat. For anyone else the section says why not; for a client with bookings it adds that bookings, payments and receipts are her records and points to switching off online booking instead. Before anything goes it asks, naming the client and what would be removed ("Their details, 2 saved addresses and 2 notes will be removed for good. This can't be undone."), with the safe choice focused and the question read out with both buttons. What goes: the profile, its saved addresses and notes, the waiting-list requests they made (linked to them, or made by their own login before their profile existed), the alerts that name the client (including the question "Is this the same person?" about a pair, from either side), the history of profiles that were combined into it (and into those before), and their online account if they have one, so that email can register again. The deletion is tied to the question: it carries what the question said would go, and if any of that changed in between (an address or note added, a request made, the person signing up) nothing is deleted and she is asked again. The Admin's own profile is never deleted here. Nothing is deleted while anyone is in the middle of booking: a time held for a visitor has no client attached until the very end of their booking, so there is no way to tell whose profile they are using, and deleting it under them would break their booking. The page says so and offers Check again. A half-made New booking for the deleted client is dropped from the Admin's tab.

**Reason:** She asked for an option to delete a client, mainly to clear test and duplicate profiles before real clients start. A client's bookings, payments and receipts are money records, and the database already refuses to remove a client they point at. Deleting those with the client would have destroyed records she may need for her accounts and left gaps in the receipt numbers, so a client with bookings is never deleted from the app.

**How it was built:** Migration `20261025100000_admin_delete_client.sql`. `client_delete_scope(client)` (inside only) counts what would go in one place, so the question and the deletion cannot disagree. `admin_client_delete_check(client)` (Admin only) reports whether the client can be deleted, the one reason if not (an Admin profile, bookings, a repeat, someone booking) and what would go. `admin_delete_client(client, request key, expected)` checks everything again inside a lock before it deletes: it takes the same email lock as signing up and combining, and locks the client row, so a booking or repeat arriving at the same moment either shows up in the checks or waits and finds the client gone. It then compares what is there with `expected`, removes the items above, deletes the login (`auth.users`) and records what it did in `client_deletions`: the id, who did it, when, and counts, never who the client was. The same press arriving twice (a dropped connection, a second tab) is answered, not done again, and if the answer is lost after the client was deleted the page checks and says they are gone. The page reads the answer from the database and decides nothing itself; it looks again just before asking, so the question counts what is there now. The database change was applied to the online Supabase project on 2026-10-13 with the owner's say-so (that one file, after a dry run) and checked there read-only.

**Limits, on purpose:** There is no undo. The question is the safeguard, and database backups are the safety net only on a paid Supabase plan (the free plan keeps none). A client who has ever had a booking, even a cancelled one, cannot be deleted from here; clearing test accounts that took bookings before real clients start is a one-off done with her say-so and after a copy of the database. This is not an erase-everything guarantee: an alert already sent to Telegram or email cannot be unsent, and backups and the sign-in service's own logs may keep copies for a while. The record of deletions can be read from the Supabase dashboard only; nothing in the app shows it. The page of a deleted client stays in the browser's history and then says the client could not be found. Hiding a client without deleting (archiving) was not built; say if it is wanted for clients with bookings.
