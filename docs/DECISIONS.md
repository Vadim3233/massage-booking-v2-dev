# VAD Massage Booking V2 — Decision Log

Updated: 2026-09-23. These are design decisions and intended requirements; implementation status belongs in `APP_PLAN.md`. Add dated entries when a decision changes, retaining earlier context.

## ADR-001 — One booking core, separate interfaces

**Decision:** Keep one Supabase-backed booking system and shared server-side rules, with distinct client and admin experiences in the same repository initially.

**Reason:** A client, Vad and a future messaging agent must receive the same availability, pricing and booking outcomes. Separate navigation and permission boundaries serve each role without synchronizing independent calendars.

## ADR-002 — Booking authority resides in the backend

**Decision:** The backend owns slot calculation, quotes, eligibility, holds, booking creation and changes. Revalidate and reserve atomically when confirming a booking.

**Reason:** Browser and conversational interfaces cannot safely enforce rules or prevent two requests taking the same slot. Meaningful tests must cover boundaries and conflicts.

## ADR-003 — Clients, accounts and channels are distinct

**Decision:** A client record can exist without an online account, booking or Telegram/WhatsApp connection. A normalized phone can help find a client; confirm saved address and verify identity for sensitive actions.

**Reason:** Vad creates client records offline, and contact details can change or be shared.

## ADR-004 — Agent-ready API without immediate Meta dependency

**Decision:** Design controlled booking operations that the website, admin and future approved integrations can call. Grant a client-facing WhatsApp agent only its necessary actions; any personal assistant uses separate admin-scoped access. Verify Meta Business Agent, Muse and WhatsApp Business Platform capabilities before choosing an integration.

**Reason:** Product access and APIs can change. The booking system must remain usable and authoritative regardless of an AI provider.

## ADR-005 — Payment and appointment state are explicit

**Decision:** Bank transfer instructions, verification, booking hold and confirmed appointment are separate concepts. A quoted or requested session is not automatically a paid booking.

**Reason:** Manual payment verification and hold expiry must be represented accurately in the app and notifications.

## ADR-006 — Documentation stays with implementation

**Decision:** Keep `docs/APP_PLAN.md` for scope, behavior and roadmap, and `docs/DECISIONS.md` for reasons behind architectural choices. Read both before substantial V2 changes and update them in the same change when decisions or status shift.

**Reason:** Repository history is easier to inspect than decisions scattered across chats. Status must be supported by code and acceptance evidence.

## ADR-007 — External agents are interfaces, not booking systems

**Decision:** Website, Admin, WhatsApp and any future Meta/Muse agent must call the same authoritative booking operations. External agents may not implement their own availability, pricing, booking-limit or conflict logic and may not write booking tables directly.

**Reason:** This prevents channel-specific behavior drift and allows an agent provider to be changed without changing the booking rules.

## ADR-008 — Agent writes require confirmation, idempotency and audit

**Decision:** Agent-triggered create/reschedule/cancel actions require explicit client confirmation, an idempotency/request key and an auditable source/actor record. Webhook or tool retries must be safe to repeat without duplicate bookings or duplicate mutations.

**Reason:** Messaging platforms and AI/tool calls can retry or repeat requests. A booking system must not interpret repeated delivery as repeated intent.

## ADR-009 — Channel identity does not replace canonical client identity

**Decision:** `clients.id` is the canonical business identity. Auth user IDs, phone numbers, WhatsApp identities, Telegram connections and other channels link to it. Phone-number matching may help identify a returning client but is not sufficient authorization for sensitive reads or changes.

**Reason:** Phone numbers can change, be shared or be entered incorrectly. Client history and booking changes need a stable record and stronger authorization boundaries.

## ADR-010 — Build agent readiness now; integrate Meta/Muse later

**Decision:** V2 will include a channel-neutral, versioned integration boundary, separate permission scopes, source/actor audit, idempotent commands and committed-event notification hooks as part of the core architecture. Actual Meta/Muse/WhatsApp agent implementation remains deferred until the core booking journeys are reliable and the current provider capabilities are verified.

**Reason:** These boundaries are inexpensive to design into the clean rebuild but expensive to retrofit after the database and booking contracts are established. They also avoid making V2 dependent on a particular external AI product.


## ADR-011 — Bounded reads and on-demand Admin loading

**Decision:** Calendar and operational reads must be scoped to the date/data range needed by the current screen. Historical data loads separately. Analytics, detailed Settings, receipts/documents and similarly heavy secondary surfaces should be lazy-loaded when opened.

**Reason:** V1 repeatedly loaded all bookings and bundled heavy Admin surfaces into the initial workspace. That increased database traffic, render work and coupling without adding product value.

## ADR-012 — Canonical records over derived or duplicated browser business state

**Decision:** Supabase canonical records are the source of truth for clients, bookings, payments and settings. Admin client lists come from canonical client data, not reconstruction from booking history. Browser storage and React state may hold temporary UI/draft/cache state only and must not become an alternative business database.

**Reason:** V1 represented booking/client data in database columns, JSON notes, React state and browser storage at the same time. The resulting contradictions and stale compatibility layers were a major reliability problem.

## ADR-013 — Maintainability changes must target ownership, not cosmetic file splitting

**Decision:** V2 will use feature-scoped components, styles and modules, but file splitting alone is not treated as a performance optimization. Performance work focuses on bounded queries, reduced duplicate work, lazy loading and smaller active bundles. Dead or permanently disabled code is removed rather than hidden.

**Reason:** V1's very large App/Admin/CSS files made regression risk high, while some runtime cost came from data-loading and repeated calculations rather than file size itself.


## ADR-014 — One visit, separate session rows

**Decision:** A booking represents one visit to one address and start time. Each person's treatment is stored as a separate `booking_sessions` row. The booking stores the summed treatment duration, while pricing and session identity remain per session.

**Reason:** This preserves the V1 client experience while permanently preventing the old `2 × 60 = 1 × 120` modelling error. It also keeps travel buffer around the visit rather than between sessions inside the same visit.

## ADR-015 — Payment has one authoritative record per booking

**Decision:** V2 uses one authoritative booking-payment record linked one-to-one with the booking. Booking status and payment status remain separate state machines; payment state is not duplicated in a second order authority and booking JSON notes.

**Reason:** V1 could disagree across order state, booking state and notes. A single payment authority makes verification, cash approval, cancellation and refund history explicit.

## ADR-016 — Calendar blocking uses one canonical block model

**Decision:** Date-specific unavailable time and Admin personal events use one canonical calendar-block model with a type/kind field and optional personal-event presentation metadata.

**Reason:** Both concepts block availability. A single scheduling-block source simplifies availability queries while still allowing Admin to distinguish blocked time from named personal events.

## ADR-017 — Client draft, finalization and payment reference (2026-09-27)

**Decision:** Keep unfinished booking inputs and an in-flight finalization request in versioned session storage; keep only the opaque hold client key in local storage. An ambiguous transport failure locks the request for retry using the identical payload and idempotency key. Store only the returned booking ID for subsequent authenticated server reads, not a browser booking database.

**Reason:** Reloads and authentication redirects must preserve the draft without creating duplicate bookings. Confirmation requires a successful finalization result or an authenticated read of the canonical booking.

**Decision:** Public bank details use explicit `VITE_BANK_*` configuration, matching V1's configuration approach. Finalization supplies the payment reference; the UI does not invent it before booking creation. Bank-transfer submission remains awaiting verification, and cash remains awaiting approval. No notification-delivery claims are made from the browser.

**Reason:** The deployed V2 finalization contract returns the reference only after the atomic transaction. A client-side reference or preliminary order would restore the V1 architecture defect. Missing bank configuration is visible and prevents bank-transfer submission.

## ADR-018 — Status changes are guarded and recorded in the database (2026-10-09)

**Decision:** `bookings.booking_status` and `booking_payments.status` may only move along the allowed transitions defined in `20261009100000_booking_status_guard_and_audit.sql` (for example `cancelled`, `completed` and `no_show` are final, and cash must be approved before it is paid). Every booking or payment creation and status change is recorded in the append-only `booking_status_events` table with the acting user, actor type and role. Admins can read the history; nobody can edit or delete it.

**Reason:** Browser roles already cannot write these tables, but SECURITY DEFINER commands, the service role and manual SQL could still make an impossible change with no record. Tests and fixtures must now reach a state by a legal path or by inserting rows in that state. History starts at this migration and is not backfilled.

## ADR-019 — Bookings waiting for payment are decided by the Admin, never by a timer (2026-10-10)

**Decision:** Nothing is cancelled automatically. A bank-transfer or cash booking that is waiting for payment keeps its time until the Admin confirms the payment or removes the booking. Removal (`admin_remove_pending_booking`) records the booking as cancelled by the Admin and rejects its payment record; nothing is deleted and no fee is implied. The Admin may also confirm a transfer the client never declared, and the Payment Review list shows every booking that is waiting, with when it was booked. Clients are limited only by the existing active-booking limit (one for a new client, five for a returning client). Clients cannot list or hold times more than 40 days ahead and need two hours' notice; Admin booking has no horizon.

**Reason:** The business is built on loyalty and personal follow-up. A client who pays late must not lose their time or be double-booked, and the Admin decides when a booking will not be paid or attended. `bookings.payment_reservation_expires_at` is kept for history but is deprecated and always null. Automatic expiry or reminders could be added later as an explicit change.

## ADR-020 — First-use scope, build order and operating choices (2026-10-10)

**Decision (owner's answers):**
- **First use:** the owner alone enters her own bookings first; clients are opened up later. Start using the app as soon as the daily core works, and add the rest while using it.
- **Build order:** (1) daily core: finish Admin New Booking; confirm/cancel/reschedule/complete/no-show with recorded reasons and history; Agenda/Today; client self-cancel and reschedule; (2) alerts; (3) schedule control (working hours, days off, overrides, block time and personal events); (4) clients (search, profile, addresses, notes/preferences, history); (5) settings screens for services, prices, areas, bank details and booking/cancellation rules, because she wants to change everything herself and not through the database; (6) waitlist. Quick contact actions (call, WhatsApp, directions) come with the daily core. Analytics, receipts, finance, diagnostics and the WhatsApp assistant stay out of scope for now.
- **Alerts:** Telegram, email and in-app for new bookings and "I've paid" claims, each with a link to the exact booking, sent from committed events (outbox). Telegram reuses the existing bot (token entered by the owner as a secret, never committed). Email uses Resend from an address on vadmassage.com (DNS records needed).
- **Client changes:** clients cancel and reschedule themselves. Inside 24 hours it is still allowed online, but the full appointment fee is recorded as due (the Admin can reduce or waive it). A booking can be cancelled free within one hour of being made. Fees are recorded; money is collected outside the app.
- **Accounts:** unchanged (sign in with email or Google as part of booking), which self-service needs.
- **Hosting and data:** booking.vadmassage.com on Vercel; start fresh with no import from V1. Test mostly on iPhone Safari, then Android Chrome.

**Reason:** Keeps the launch to what is needed to run the diary, in an order that lets real use find problems early. Supersedes the open question in ADR-019 about reminders: alerts are in scope, automatic cancellation is not.

## ADR-021 — Booking lifecycle: late fees, refunds and how changes are made (2026-10-10)

**Decision:** The Admin completes, no-shows, cancels and reschedules bookings only through retry-safe commands (`admin_complete_booking`, `admin_mark_no_show`, `admin_cancel_booking`, `admin_reschedule_booking`, `admin_settle_late_fee`, `admin_record_refund`), each recorded in the status or schedule history.
- A cancellation or change is free more than 24 hours before the appointment and free for one hour after the booking was made, even for a same-day appointment. Exactly 24 hours before is not "more than 24 hours", so it is charged.
- Inside 24 hours a client-requested cancellation or change is still allowed. The full appointment price is recorded as a late fee due; the Admin may set any amount from zero to the full price (zero waives it, and the standard amount stays on record). A change the Admin makes on her own account never charges the client. A second late change does not add a second fee.
- A no-show records the full price as due unless the Admin chooses a lower amount.
- Money is collected outside the app. If a paid booking is cancelled, the fee is kept from the payment and the balance is recorded as a refund due until the Admin records it as sent.
- Rescheduling uses the same availability engine as booking, ignoring the booking being moved; the Admin cannot place a booking in a time the engine would refuse. Admin booking has no 40-day horizon (a 365-day sanity limit remains).
- The fee rule lives only in the database (`late_fee_standard_gbp`); screens ask `admin_late_fee_preview` and never repeat it.

**Reason:** These are the owner's answers (ADR-020 and follow-up): clients should not have to message her for routine changes, loyal clients are treated kindly, and every money-affecting outcome is visible and reversible by her decision. Client self-service cancel and reschedule will call the same rule and engine.

## ADR-022 — Clients manage their own bookings at /account (2026-10-11)

**Decision:** A signed-in client (including a guest on the same device) sees their bookings at `/account` and can cancel or change the time without messaging the Admin. The page asks the database for everything it shows: the terms (`get_my_change_terms`), the times (`get_my_booking_availability`), and the result (`client_cancel_booking`, `client_reschedule_booking`). Inside 24 hours the change is allowed, but the client must tick that they understand the exact late fee; the command sends that fee back, and if it no longer matches (the 24-hour mark passed while the page was open) it refuses and the client reviews again. Changes use the client booking rules: two hours' notice, 40 days ahead, the same availability engine. Errors shown to clients are a fixed set of kind sentences; technical messages are replaced.

**Reason:** The owner wants routine changes to happen without a message to her, with the fee rule applied consistently and visibly. The Admin is told through the same event stream as other changes (`booking.cancelled` and `booking.rescheduled` carry `initiated_by: client`).

## ADR-023 — Alerts are written by the database and delivered by a small sender (2026-10-11)

**Decision:** When a booking event is committed, the database writes the finished message (title, text, link to the exact record) into `notification_deliveries` for three destinations: an in-app alert for the Admin, a Telegram message and an email to her, and where relevant an email to the client. In-app alerts need nothing outside the database. `api/dispatch-notifications.js` delivers the Telegram and email rows, records success or failure, and retries failures after 2, 8, 18 and 32 minutes (five attempts). It runs only for a caller who holds `CRON_SECRET` and uses the server-side service key, which is never in the browser or repository. The Admin is alerted about new online bookings, "I've paid", cash requests and client cancellations or moves, never about her own actions. Clients are emailed when a booking is confirmed, cancelled, moved or refunded.

**Reason:** One tested place owns the wording and the rules for who hears what, so Telegram, email and the app never disagree. The in-app list works even if Telegram or email is down. A narrow, secret-protected sender keeps the powerful key off the client and makes delivery failures visible rather than silent. Setup steps that need the owner's accounts are in `docs/NOTIFICATIONS_SETUP.md`.

## ADR-024 — The Admin edits her own schedule, with warnings instead of silent clashes (2026-10-11)

**Decision:** Working hours (usual week), special days (days off or different hours for one date) and blocked time or personal events are edited from the Admin app, directly in their tables, which already allow only the Admin and enforce valid times. Before saving a day off, shorter hours or a block, the screen asks `admin_schedule_conflicts` which live bookings (pending or confirmed, including their travel allowance) it would clash with, shows them by name, and lets her save anyway. Existing appointments are never moved or cancelled automatically. Times are chosen in 30-minute steps to match the availability engine, and the start-and-end rules are checked on screen with plain sentences before the database checks them again. Blocks make the time unavailable for treatment and for the travel around it (the availability engine already treats blocks that way).

**Reason:** She wants to change her hours, take days off and block personal time without touching the database. A warning that names the booking is safer than refusing the change, because a day off or a dentist visit may be unavoidable, and safer than silently leaving a booking in an impossible slot.

## ADR-025 — The Admin manages clients from a directory and profile (2026-10-11)

**Decision:** `/admin/clients` searches the canonical client records (the existing bounded search: 20 best matches) and adds new clients with an address. A client's profile shows contact links, a summary (visits, money paid, upcoming, last visit, next appointment, late fees and refunds still due, all computed by `admin_client_summary` on the server), editable details, saved addresses (add, change, make default, remove), private notes, booking history (loaded in pages of 15), and a switch for online booking. "New booking" from a profile opens the booking wizard with that client already chosen. Editing a client goes through `admin_update_client`, which refuses an email or phone another client already uses, so records cannot silently duplicate. A client's record, their login account and their bookings stay separate things: editing contact details does not change a login, and removing an address never changes a past booking, which keeps its own copy.

**Reason:** The owner needs to look someone up, see what they owe and when they last came, and correct details without the database. Keeping the contact fields behind one checked command prevents duplicate clients, and keeping money and visit totals on the server avoids loading a whole booking history to add up a number.

## ADR-026 — Services, prices, areas, extras and bank details are edited in the app (2026-10-11)

**Decision:** The Admin edits treatments (with the three lengths and their prices), extras, and areas (travel surcharge and congestion charge) from More. She can add, change, hide or show, and reorder them. Prices and fees apply to new bookings only; existing bookings keep the price they were booked at (they store their own copy). Hiding an item removes it from what clients can choose but keeps it for history. A shown treatment must offer at least one length. New items get a plain web-safe name derived from their name, kept unique. Bank details are saved through `admin_save_bank_details` (name, optional bank, six-digit sort code, eight-digit account number, optional note) into the Admin-only `business_settings` table. Clients receive them only through `get_bank_details()`, and only when they hold a client record (guests included). The build-time `VITE_BANK_*` values remain as a fallback for when nothing is saved.

**Reason:** She wants to change her prices, areas and bank details without touching the database or redeploying. Keeping bank details out of a public table and behind a function that answers only signed-in clients limits who can see them, and the fallback keeps current behaviour working until she has entered her own.

## ADR-027 — The booking rules are settings the Admin can change (2026-10-11)

**Decision:** Six rules live in `business_settings` and are edited at More, Booking rules: how many days ahead clients can book (40), hours of notice (2), free-cancellation window (24 hours), grace period after booking (60 minutes), and how many upcoming bookings a new client (1) or returning client (5) may hold. The booking, availability, reschedule and fee functions read them through `business_setting_int`, which falls back to the default if a value is missing or unusable, so a bad setting can never break booking. A rule applies from the moment it is saved to anything done afterwards; bookings already made and fees already recorded are not recalculated. Notice is now an exact time comparison (the appointment must start at least that long from now, across midnight), so a notice longer than the rest of today works correctly. The booking pages read the few public numbers they need (days ahead, notice, free window, grace) from `get_booking_rules()` so the date picker limit and the wording ("up to 24 hours before…") follow the settings. Admin booking is not limited by the horizon or notice. Ranges are enforced by the database and checked on screen first.

**Reason:** The owner wants to change these rules herself without a developer. Keeping every use of a number behind one reader means the wording, the limits and the fees cannot drift apart.

## ADR-028 — A simple waitlist that never books by itself (2026-10-11)

**Decision:** When the day a client chooses has no suitable times, the booking page offers to take their name, phone or email, a time of day (any, morning, afternoon or evening), the treatment length and an optional note. Anyone may do this without signing in (they are choosing a date before sign-in); a request is limited per phone number or email (three open requests), overall (300 open), and the same person asking twice for the same day and length is one request. The Admin sees open requests at More, Waitlist, soonest day first, each with the times that could be booked for that person right now (computed by the same availability engine as booking, inside their preferred time of day), quick call, WhatsApp and email links, and a private note. She can record that she offered a time, mark it not answered, close it as booked or no longer needed, and book for a client straight from the request when they already have a client record. She is alerted (in the app, Telegram and email) when someone joins and when a booking is cancelled or removed on a day people are waiting for. Nothing is ever booked, offered or messaged to the client automatically.

**Reason:** The owner asked for a waitlist but a workable one. Anyone's contact is taken only when there is genuinely nothing free, matching the real availability rules shows her at a glance who she can help, and keeping every offer and booking in her hands matches how she works with clients.

## ADR-029 — Design polish: the brand's type, one set of colours, and a calmer progress line (2026-10-11)

**Decision:** Headings use Playfair Display and interface text uses Inter (loaded from Google Fonts with a Georgia and system-font fallback), as the brand calls for. Every colour used by the app's stylesheets is now a named value in `src/index.css` (`--ink`, `--green`, `--gold`, `--danger` and so on), so the look can be changed in one place. On a phone the eight-step list in the booking flow becomes one line ("Step 4 of 8 · Date & Time") and a thin progress bar; the full list stays for screen readers and for wider screens. The brand mark is a small monogram instead of plain letters. The tab icon, title and description are VadMassage's own rather than the project template's. Buttons give a small response to touch and hover, and all motion is switched off for people who ask for reduced motion. Admin page titles use the heading face. Unused template leftovers (`App.css`, three sample images) were removed because nothing imports them.

**Reason:** The first impression for a client should feel warm and personal, and the screens should look like one product. Fonts from Google send visitors' addresses to Google; if that is not acceptable they can be served from the site itself instead (noted in `GO_LIVE_CHECKLIST.md`).

## ADR-030 — Repeating bookings are a standing rule, not a year of bookings (2026-10-08, built 2026-10-09)

**Decision:** A repeating booking is stored as one standing rule (weekday, time, length, area, address, start date, optional end date). The rule keeps that weekly slot free in the availability search until it ends; skipped dates are released. Only the next one or two sessions exist as real bookings, and the app creates the next one when the previous is completed or cancelled. Only the next booking asks for payment; the client is reminded 7 days before the following session (the number of days is a setting). Nothing is cancelled automatically: an unpaid session is shown to the Admin as overdue and she decides. Cancelling one session skips that date and the repeat carries on, under the usual 24-hour fee rule; the one-hour free-cancel grace does not apply to sessions the app creates itself. A new price applies from the next session created, and the client is told. The Admin creates repeats from a client's profile first; a client-facing "repeat weekly" option comes later. The client booking horizon is raised from 40 days towards a year through the existing setting.

**Reason:** Some regulars book the same weekday every week. A year of real unpaid bookings would crowd the Review screen and block slots if a client drifted away, while a standing rule keeps their slot safe without that clutter. Building the Admin side first lets her get the rules right with clients she already knows.

**How it was built:** `booking_series` holds the rule and `booking_series_skips` the dates that are not booked (skipped, cancelled, moved, or a clash). The held slot is a `calendar_blocks` row of kind `series_hold`, so the availability search and clash checks needed no change. The first booking is made with the repeat through `admin_create_series`, which calls the same `admin_create_booking` command as a new booking. `run_series_maintenance` (called by the sender endpoint, at least daily) tops up the holds and makes each booking when its date is inside the reminder window (`series_payment_reminder_days`, 7 by default, editable in More, Booking rules). It acts as the Admin who made the repeat so the same availability, price and snapshot rules apply. If a time is no longer free the date is skipped and the Admin is alerted instead of anything being forced. The client sees the usual booking page; the booking is announced by a "time to pay" message instead of the ordinary "booked" one. Not built yet: a client-facing "repeat weekly" option, and clients skipping a date from `/account`.

## ADR-031 — Blocked time runs over a range of dates and hours (2026-10-09)

**Decision:** Blocking time takes a start date and time and an end date and time, like an event in a phone calendar, so one block can be a holiday, a few days, "Friday 14:00 to Monday 09:00" or two hours in a day. Each day keeps its own row in `calendar_blocks`, so the availability search, the calendar and the clash check work as they did; rows that belong to one block share a `group_id` and are saved, changed and removed together by `admin_save_block_range` (one command, so a block is never half saved). The clash check, `admin_block_range_conflicts`, lists every live booking the range covers, day by day, and nothing is moved or cancelled for her. A block can cover up to a year. Blocked time can be added, changed and removed from the Calendar and from More, Working hours, Special days, where upcoming blocks are listed. Special days (a day off or different hours for one date) stay as they were.

**Reason:** She wanted to block more than one day, or only some hours, without adding each day by hand. Splitting a block into one row per day keeps every existing rule that reads blocks correct, instead of teaching each of them about ranges.

## ADR-032 — One design language and shorter journeys, for clients and for the Admin (2026-10-12)

**Decision:** Both sides now share one set of building blocks (`src/index.css` tokens, `src/ui.css`). Colour says whose turn it is: amber means it needs the Admin, a dashed outline means the client's turn, green is settled, grey is finished or cancelled, plum is a no-show and red is a late fee. Every screen has one filled button for the next step, outlined buttons for the rest, quiet text for going back, and a red outline (filled only inside a confirmation) for anything destructive. Headings use Playfair Display with lining numerals and, on the client side, one italic gold phrase; everything else is Inter.

For the Admin: a bottom tab bar on a phone (a rail on a wide screen) with badges for what needs her, a "Needs you" strip at the top of the Agenda with Verify and Approve one tap and one confirmation away, toasts that say what just happened, loading shapes instead of the word "Loading", and Alerts grouped by booking. New booking is one numbered page where treatment and length are tapped, the time comes from the same picker clients use, and the client's usual choices are already filled in.

For clients: choosing a length goes straight on to choosing a time; the time page opens on the first day with room and shows the full days before it; looking at other days never lets go of a time that is held; the review is a ticket with preferences behind one optional section and a price that follows the choices without a button; "Continue as guest" is the plain way on and signing in waits behind "Returning client?". A confirmed appointment can be added to a calendar, a regular client is offered their usual booking, links such as `/?area=chelsea&treatment=massage&minutes=60` open the booking part-way through, and moving an appointment uses the same day-and-time picker.

**Reason:** The owner asked for fewer clicks and scrolls, more defaults, clearer typography and an app that feels modern from both ends. Doing it as one design language keeps the two sides looking like one product and keeps every later screen cheap to build. Nothing about the rules changed: availability and travel buffers, the cancellation window and fees, the payment rules (a transfer is never marked paid by the client; cash needs a deliberate confirmation), the order of the booking steps and the three lengths are as they were, and there are no database changes in this work.

**Added later the same day:** The Agenda, the Day view, To check and Alerts keep what is on screen while they are read again, and read again whenever the Admin comes back to the app (a home-screen app has no pull to refresh). The Agenda re-reads whatever months are on show a month at a time, because one read is limited to 31 days. Cancelling offers No fee, Standard fee and Full price in one tap, and moving an appointment uses the shared day-and-time picker; both keep their buttons in reach while the form scrolls, as does Block time. Appointment cards put the treatment and the postcode on one line. On the booking page the areas come before the three steps, and on the payment screen the terms sit right under the bank details; the main button is always pressable and, if the terms are not ticked yet, takes her to the box and says why (a greyed button gave no reason). Nothing about when a booking counts as paid changed: the client's button only reports that they have made the transfer.

**After an independent review and a tester using the app on a phone:** a cancellation never goes ahead on a fee the Admin has not seen (the standard fee only fills in a fee she has not chosen, and if it cannot be looked up she chooses one); a refresh that fails just after the phone wakes is tried once more, quietly, before anything is said; a reserved booking has no way back, so the payment screen says so and offers "Change the time or cancel this booking" (the account page); a phone number or postcode that cannot be right is named beside its field before a time is reserved; and a second tap that lands just after a screen has changed is ignored for 0.4 seconds, so it cannot choose the next treatment or length by accident. The "New test client" testing helper is limited to development builds, so it can no longer be reached on the live page with `?test=1`. Every appointment still to come has a Directions button beside its status (Google Maps, the same link as in the booking details), as a control of its own next to the card, never inside it. Tests that place a booking relative to the clock were made safe at any time of day. Still open on purpose: the client's page counts an appointment earlier today as upcoming, and guests who book twice appear twice under Clients (a guest's email is never trusted to link them to an existing client).

**How it was built:** `DayTimePicker.jsx` is the one picker (booking, moving an appointment, Admin New booking). The booking store gained `selectSlot(start, date)` (the viewed day is saved only with a chosen time) and `refreshQuote` (the price updates without locking the screen, and a price for choices that have since changed is dropped). Small pure modules carry the logic that can be tested without a browser: `timeOfDay`, `dateStrip`, `usualBooking`, `deepLink`, `calendarFile` and `groupAlerts`.

## ADR-033 — Two profiles that might be one person are combined only when the Admin says so (2026-10-13)

**Decision:** Someone who booked as a guest and later registers with the same email now gets a profile of their own instead of an error, and the app never combines profiles by itself. The database notices profiles that share an email or a phone number (a phone number is compared by its last ten digits, so 07700 900123 and +44 7700 900123 match). All such pairs are listed in a "Might be the same person" note at the top of the Clients page, and every client's page has "Combine with another client…" for pairs the app cannot spot. When a pair has something to combine (a booking on either profile), the Admin is also told once in the app: "Is this the same person?". She sees the two profiles side by side and answers: combine them, "No, different people" (remembered, so she is never asked about that pair again) or decide later. Combining asks once more, because there is no undo button.

Two profiles that each have their own login are never offered and can never be combined. Where one profile has a login, that one stays. Where neither has, she chooses; the suggestion is the one she added herself rather than a guest, then the one with more bookings, then the older. A guest's profile can be reached from the browser that made it, and nothing proves who is behind it, so it is never suggested over one the Admin added. Where a mistake is easier to make the screen says so and "Yes" is no louder than "No": the first names differ, or only a phone number matches (a phone number typed when booking is never checked, an email that has been confirmed is). When a guest's profile goes, the confirmation says the guest will then see and change those bookings only by signing in.

The profile that goes hands everything to the one that stays: its bookings (status, payment, fees and the address each was made for are untouched), repeat bookings, notes, addresses, waitlist requests and any time still held. A repeat keeps a copy of the booking it makes each week, which names the client and perhaps a saved address; both follow the move, or the daily job could not make the next session. An address the other profile already has is not copied twice, but only when their entry instructions agree or one has none; what the copy knew (instructions, a label) is kept on the original, and the whole copy is saved in the history. The profile that stays also gains an email, phone number or last name it lacked, the earlier "client since" date, and keeps online booking switched off if it was off on either. A private note on it says what was combined, and the profile that went is saved whole in `client_merges`, so a mistake can be put right by hand.

**Reason:** A guest's email has never been checked, so using it to link a guest to an existing profile would hand that person someone else's bookings and addresses if the email was mistyped or borrowed; and refusing the registration (the old behaviour) left a real client stuck with a message they could not act on. The Admin is the one person who can tell whether two entries are one client, it takes her a few seconds, and it only happens when the app sees a likely match.

**How it was built:** Migration `20261022100000_same_person_clients.sql`. `activate_my_client_account` now ignores profiles that belong to a guest session when it checks whether an email is already taken (a different real login on the email still blocks, as before). `client_duplicate_pairs` finds pairs by lookup (an index on the phone key as well as on the email), so saving a profile stays quick with thousands of clients. A trigger on `clients` raises `client.possible_duplicate` when a profile is saved with an email or phone, but only one new question per save, only about a pair with a booking on either side, and never twice about a pair, so nobody can flood the Alerts page by making many profiles with one email; every pair still shows on the Clients page. The alert is written by `plan_client_notifications`: it says what matched and does not claim when anything happened, and it is in the app only, because nothing about it is urgent. `client_not_same` holds her "different people" answers and `client_merges` the history of every combine (the whole profile that went, which rows moved, who did it and when; readable by the Admin only). Four Admin commands do the work: `admin_possible_duplicates`, `admin_combine_preview`, `admin_keep_clients_separate` and `admin_merge_clients`. The last is one command, all or nothing, and safe to repeat: the same request key returns the same answer. It takes the same email lock as registration and locks a repeat before its client, as the repeat job does. Because people she calls "different" will often share an email or phone, `admin_update_client` now checks only a value that is being changed (it used to refuse any save while another profile shared the email or phone, so such a pair could not even have a name corrected). The screens are `CombineClients.jsx` (route `/admin/clients/combine?a=…&b=…`, which is also where the alert opens), `PossibleDuplicates.jsx` and `CombinePicker.jsx`; an alert may open only pages inside the Admin (`adminPageFromLink`; the old check ignored digits, so the repeat-clash alert's link to a client never opened).

**Found by an independent review and fixed before release:** the weekly repeat's stored copy still named the old profile, so after a combine the daily job would have failed every week, released the slot and sent false "no longer free" alerts; a copy of an address could carry entry instructions that were then lost; the check for matches read every client on every save (4 seconds at 8,000 clients; now milliseconds); anyone could raise many alerts with many guest profiles; and a guest could be suggested as the profile to keep.

**Limits, on purpose:** A guest who comes back on a new phone or browser makes a new guest profile each time; each one is combined by hand. Pairs that already exist when the change is applied are listed on the Clients page but raise no alert until one of the two is next saved. A registration can book online until the Admin combines it with a profile she had switched off, because nothing links them before she says so. `client_merges` keeps the removed profile's name, email and phone; if a client's data is ever to be erased, those rows go too. There is no Telegram message or email for this alert. The database change was applied to the online Supabase project on 2026-10-13 with the owner's say-so (before that, the preview of the screens showed a plain error when she tried to combine two profiles, as expected); on a project without it the Clients note stays hidden and the combine screen shows a plain error.

## ADR-034 — A receipt is made from a paid booking, kept as it was, and sent with the tools already there (2026-10-13)

**Decision:** Receipts were out of scope in ADR-020; the owner has now asked for them so she can send one to a client who asks after a booking. A booking whose payment has been marked as received shows a "Receipt" button on its page. Opening it the first time makes the receipt and gives it the next number (`VM-2026-0001`, `0002`, and so on, with no gaps; the year is the London year and the numbers start again each January); opening it again shows the same one. It carries her business name and contact details (and an address only if she saved one), who it is for and the booking reference, the appointment (day, time and length), one line for each treatment, extra, travel charge and congestion charge, the total paid, how and when it was paid, and an optional note and closing line. It never shows the client's treatment address, says nothing about VAT (she is not VAT-registered, and it is not a VAT invoice) and says nothing about card payments. She sends it by email (from the app, text only, no PDF), by WhatsApp (a link that opens the client's chat with the receipt already typed in) or through the phone's share sheet, which copies the text on a computer.

A receipt can only be made for a confirmed or completed booking whose payment is marked as received for exactly the booking's total. It is refused, in plain words, for a booking still waiting for payment, a cancelled booking (even if a late fee was kept), a missed appointment and a refunded payment. If the treatment lines on the booking do not add up to its total, the booking's own subtotals (treatment, extras, travel, congestion) are used instead; if neither adds up, no receipt is made rather than a wrong one. Her business details are saved once (More, Receipt details) and are needed before the first receipt.

A receipt is kept as it was on the day it was made: a later change to a price, a name or her own details never alters it. **Edit** corrects the words on that one receipt: who it is for, a note, the words of each line, and her details. The amounts, the receipt number, and how and when it was paid are never editable, because they must match the money received (the payment date is the day she marked the payment as received). Every earlier version is kept (`booking_receipt_revisions`). If the appointment is moved after the receipt was made, the receipt says so and "Update the date and time" copies the new date and time from the booking; a booking whose price no longer matches the receipt is flagged but cannot be edited from here (nothing in the app changes a price after payment).

The email uses the same queue and sender as every other email (ADR-023). The receipt reports only what is known about the newest email of it: waiting for the sender, sent, not through yet and trying again by itself, or given up after five tries. "Emailed" is never shown for an email that is only queued. The screen holds the request key of an email that was asked for but not confirmed, so pressing Email again after the connection dropped can never send it twice; once an answer arrives, or the receipt is changed, the next press is a new email. After an edit, a line says the email already sent has the old words. An email still waiting after ten minutes is shown as "still waiting to be sent", with no promise of a quick send (the sender may not be running); one that was cut off on its last try is shown as failed, and one whose delivery record is gone is never called sent.

A receipt cannot be sent or changed once its booking has been cancelled or marked as missed, or its payment refunded, even from a screen that was already open (the database refuses). A receipt email that is still waiting to go, or waiting to be tried again, is stopped at that moment, so the sender never delivers "Total paid" for money that was handed back; an email already being handed to the mail service at that very instant cannot be stopped. The booking page then shows a note that a receipt was made, and whether it was emailed.

**Reason:** She asked for a receipt she can send. Keeping it as a record of money received makes the simple rules possible: nothing on it can disagree with the booking's payment, the numbering has no gaps, and the same words go to the email and to the message she shares. No PDF, address or VAT, because she said she does not need them.

**How it was built:** Migration `20261023100000_booking_receipts.sql`. `booking_receipts` (one per booking, the frozen content, who made it and when, when it was emailed and last edited), `booking_receipt_revisions` and `receipt_counters` have row security on and no direct access for anyone; everything goes through Admin commands (definers with an empty search path, closed to anonymous and guest sessions): `admin_receipt_details` and `admin_save_receipt_details`, `admin_issue_receipt`, `admin_get_receipt` (looks without making one), `admin_edit_receipt` and `admin_email_receipt`. Internal helpers (`build_receipt_snapshot`, `receipt_refusal`, `receipt_message`, `receipt_json`, `receipt_clean_text`, `receipt_check_business`) cannot be called from outside. `receipt_message` is the one place the words are written, used by the email and by the share text. Opening, editing and emailing one receipt queue up behind the same per-day lock the cancel, move, no-show, refund and payment commands use, and then behind each other for that booking, so a receipt is never made, changed or sent from a booking that is being cancelled at that moment, and a double tap cannot make two receipts or use up a number. Two triggers (`stop_receipt_emails`, on a booking becoming cancelled or missed and on a payment leaving "paid") stop a receipt email that has not gone yet. The email is a normal client delivery (`booking.receipt_emailed`, deduplicated by the request key) with the title "Your receipt from <business> (<number>)"; making and editing a receipt are recorded too. Text is tidied: every kind of line break (including the separator some phones type) becomes a plain one, and in a one-line field a space; control characters and the ones that flip the direction of text are refused; marks that cannot be seen (zero-width space, direction marks, the byte order mark) are dropped; and the word the sender swaps for a web address ("{link}") is taken out until none is left, so it cannot be rebuilt from pieces. The same tidying is applied to text that comes from elsewhere (the client's name, the treatment, extra and area names on the lines, the greeting), and a name longer than 120 characters on a receipt is cut to fit. The screens are `ReceiptPanel.jsx` (the receipt, Edit, sending, and `ReceiptNote` for a cancelled booking), `SettingsReceipts.jsx`, `receiptsApi.js` and `receiptState.js` (what may be said about an email).

**Found by an independent review and fixed before release:** a receipt could be emailed or edited after its booking was cancelled or its payment refunded, because only the screen hid the button; the screen said "Emailed" the moment an email was queued, even if it later failed; a dropped connection followed by a second press could send two emails; a receipt kept the old date after its booking was moved, with no warning; a missed appointment could be given a receipt; and odd characters, an over-long name and the sender's link word were not handled.

**A second independent review, of the fixes, found and I fixed:** a receipt email still waiting to be sent would have gone out after the booking was cancelled or refunded (it is now stopped); the lock described above was only for one receipt and not shared with the cancel and refund commands (it now is, and a test proves the day lock is taken); a request key kept after a dropped connection could swallow a later, deliberate resend (it is now forgotten once the receipt has been read again); "it is sent within a minute" was a promise nothing kept (it now says it usually goes within a few minutes, and says it is still waiting after ten); a receipt whose delivery record was gone was called emailed; the link word could be rebuilt from nested pieces, a line separator passed the one-line rule, and names on the lines were not tidied; focus was lost when leaving a booking for the receipt details. Several tests could not fail (a check that every Admin command has an empty search path passed for one that had none, an address check looked at a key that never exists, a count of used numbers counted nothing) and are repaired; tests were added for a cancel, refund or missed appointment after a receipt, two presses at the same moment, a second year's numbering, two sessions, odd text, and every command refusing a guest.

**Limits, on purpose:** A cancelled booking has no receipt even where a late fee was kept, and neither has a missed appointment; say so if that should change. Two people changing one receipt at the same moment: the last save wins, and the earlier version stays in its history. The history is protected by having no direct access, not by a database lock against deletion; a booking that has a receipt cannot be deleted until its receipt is (on purpose, as a money record), so test data is cleared in this order: `booking_receipt_revisions`, `booking_receipts`, then `receipt_counters` (to start the numbering again), then the bookings. Receipts made while trying the app out use up numbers; clear them before real clients start (see the go-live notes). The number is given when she first opens a receipt, not when payment is received. Email delivery depends on the same sender settings as other emails and has not been tried with the real provider. An email already being handed to the mail service when the booking is cancelled cannot be stopped. Esc closes the whole booking window, as it does for every form in it, and loses a half-typed Edit. The database change was applied to the online Supabase project on 2026-10-13 with the owner's say-so (that one file, after a dry run) and checked there read-only; until then the receipt screens showed a plain error on a preview.

## ADR-035 — The Admin can choose any time for a new booking, but never a double booking (2026-10-13)

**Decision:** The New booking page still offers only the usual times: a day's appointments are kept in one run with a 60 minute gap between them, inside working hours (so on a day worked 14:30 to 17:30 with 14:30 to 15:30 booked, only 16:30 is offered). Under them the Admin has a **Show all times** button. It lists every half hour of the day, from 06:00 to the last start that finishes by midnight. The usual times look as before; the others are dashed, and choosing one says in plain words what she is setting aside: a shorter gap than her usual 60 minutes, the time being outside her working hours or on a day off, or falling in blocked time or a personal event. The same note is repeated beside the price. A time that would overlap another appointment, or one a client is in the middle of booking, is greyed and cannot be chosen; tapping it says what it clashes with. Also refused, by the database: a time that has already begun, one that would run past midnight, and one more than a year ahead. While a client is part-way through booking that day (a time is held for them for a few minutes), unusual times are paused as well: the database refuses them and the screen says so, because an unusual appointment elsewhere that day could take away the held time (a held time is only confirmed if it is still a usual time when the client presses Confirm). Otherwise it is an ordinary confirmed booking with the usual 60 minute travel allowance recorded. A repeating booking is only offered at usual times (the weekly bookings that follow are made at usual times only), so choosing an unusual time switches the repeat off.

**Reason:** She knows more than the rules do: a shorter gap when two clients live next door, a longer day, an evening. Keeping the rules as the default and showing every time with the reason for each makes setting one aside a deliberate act, and refusing a double booking prevents the one mistake that cannot be undone from happening by accident.

**How it was built:** Migration `20261024100000_admin_any_time.sql`. `admin_booking_times(date, minutes)` (Admin only) returns her working hours that day, what is booked (and held by a client who is booking), blocked time, and every start with two facts: whether it is a usual time (exactly the times `admin_booking_availability` offers) and whether it overlaps another appointment or a held time (`admin_time_clash`, an inside helper shared with the booking command). `admin_create_booking` accepts an optional `any_time` (yes or no; anything else is refused). With it only the checks above remain; without it nothing changes. `admin_create_series` refuses `any_time`. The wording of what is being set aside is written by the screen (`times.js`) from what the database reports. The shared day and time picker gained an optional footer for the button; the client booking page and moving a booking do not use it. The database change was applied to the online Supabase project on 2026-10-13 with the owner's say-so (that one file, after a dry run) and checked there read-only.

**One change to the shared availability engine, found while building this:** `compute_booking_availability` works out the times offered from the first and last appointment of the day. Each of the two candidate times was checked against only one end of the working window: the time before the first appointment against opening time but not closing time, and the time after the last against closing time but not opening time. That never mattered while every appointment lay inside working hours. With any-time bookings it would have let an appointment at 06:00 offer clients 08:00, before a day that starts at 10:00. Both ends are now checked for both. A day on which every appointment is inside working hours is offered exactly the times it was before (the existing availability tests are unchanged and pass), and tests prove the loophole is closed, including through the call the public booking page makes.

**Limits, on purpose:** Starts stay on the half hour. Moving an existing appointment (Reschedule) still offers the usual times only. After an unusual booking, the rest of that day is usually closed to clients, because the first and last appointments of the day bound what is offered. The app does not warn about the gap between two appointments that were both set aside on purpose. A repeating client's weekly booking is made at a usual time only, so an unusual booking on a day when a repeating client's time is kept free may stop that week's repeat; the screen warns when that day has one. The sticky Create booking bar covers whatever is under it while scrolling, as it always did, so an accessibility checker can flag a time under it at one scroll position (reaching a time by keyboard keeps it clear of the bar).

## ADR-036 — A client with no bookings can be deleted; a client with bookings cannot (2026-10-13)

**Decision:** At the bottom of a client's page, **Delete this client…** removes someone added by mistake, a profile made twice, or a made-up test profile. It is offered only when the client has no bookings and no weekly repeat. For anyone else the section says why not; for a client with bookings it adds that bookings, payments and receipts are her records and points to switching off online booking instead. Before anything goes it asks, naming the client and what would be removed ("Their details, 2 saved addresses and 2 notes will be removed for good. This can't be undone."), with the safe choice focused and the question read out with both buttons. What goes: the profile, its saved addresses and notes, the waiting-list requests they made (linked to them, or made by their own login before their profile existed), the alerts that name the client (including the question "Is this the same person?" about a pair, from either side), the history of profiles that were combined into it (and into those before), and their online account if they have one, so that email can register again. The deletion is tied to the question: it carries what the question said would go, and if any of that changed in between (an address or note added, a request made, the person signing up) nothing is deleted and she is asked again. The Admin's own profile is never deleted here. Nothing is deleted while anyone is in the middle of booking: a time held for a visitor has no client attached until the very end of their booking, so there is no way to tell whose profile they are using, and deleting it under them would break their booking. The page says so and offers Check again. A half-made New booking for the deleted client is dropped from the Admin's tab.

**Reason:** She asked for an option to delete a client, mainly to clear test and duplicate profiles before real clients start. A client's bookings, payments and receipts are money records, and the database already refuses to remove a client they point at. Deleting those with the client would have destroyed records she may need for her accounts and left gaps in the receipt numbers, so a client with bookings is never deleted from the app.

**How it was built:** Migration `20261025100000_admin_delete_client.sql`. `client_delete_scope(client)` (inside only) counts what would go in one place, so the question and the deletion cannot disagree. `admin_client_delete_check(client)` (Admin only) reports whether the client can be deleted, the one reason if not (an Admin profile, bookings, a repeat, someone booking) and what would go. `admin_delete_client(client, request key, expected)` checks everything again inside a lock before it deletes: it takes the same email lock as signing up and combining, and locks the client row, so a booking or repeat arriving at the same moment either shows up in the checks or waits and finds the client gone. It then compares what is there with `expected`, removes the items above, deletes the login (`auth.users`) and records what it did in `client_deletions`: the id, who did it, when, and counts, never who the client was. The same press arriving twice (a dropped connection, a second tab) is answered, not done again, and if the answer is lost after the client was deleted the page checks and says they are gone. The page reads the answer from the database and decides nothing itself; it looks again just before asking, so the question counts what is there now. The database change was applied to the online Supabase project on 2026-10-13 with the owner's say-so (that one file, after a dry run) and checked there read-only.

**Limits, on purpose:** There is no undo. The question is the safeguard, and database backups are the safety net only on a paid Supabase plan (the free plan keeps none). A client who has ever had a booking, even a cancelled one, cannot be deleted from here; clearing test accounts that took bookings before real clients start is a one-off done with her say-so and after a copy of the database. This is not an erase-everything guarantee: an alert already sent to Telegram or email cannot be unsent, and backups and the sign-in service's own logs may keep copies for a while. The record of deletions can be read from the Supabase dashboard only; nothing in the app shows it. The page of a deleted client stays in the browser's history and then says the client could not be found. Hiding a client without deleting (archiving) was not built; say if it is wanted for clients with bookings.

## ADR-037 — The link in a booking email opens that booking on any device, without signing in (2026-10-13)

**Decision:** The "See or change your booking" link in an email to a client now ends in a private code (`/account?booking=<booking>#key=<code>`). Opening it shows that one booking and lets the client cancel it or move it, on any phone or browser, with no sign-in: a guest who booked on the website, a client the Admin added (who has no login), and a client with an account who is signed out or signed in as someone else, the Admin included. It is the same page and the same rules as when signed in: inside the free-change window a late fee has to be acknowledged first, the notice, availability and fees are untouched, and the client and the Admin are emailed and alerted exactly as before. The link opens that one booking and nothing else: the list of all of someone's bookings still needs a sign-in, and the page says so. A code that is wrong, mistyped, old, or belongs to another booking gets one plain answer ("This link is not valid or has expired. Please contact Vad."), which does not say whether the booking exists. A code stops working 30 days after the appointment (and never sooner than 30 days after the email). Every email to a client about a booking gets its own fresh code; the Admin's emails and Telegram messages get none.

Anyone who holds the link can manage that booking, as with a booking link in any email, so the booking is only as private as the inbox it was sent to. Once the page has opened, the code is taken out of the address bar (so a copied address or a screenshot of the page does not carry it) and kept for that tab only, so a reload still works.

**Reason:** The owner tried the guest journey herself and met two dead ends that were one problem: after paying by transfer as a guest, "Go to my bookings" said there were no bookings, and the link in the "your appointment is confirmed" email said something went wrong. The booking page only ever knew the session of the browser that made the booking; on another phone, in a mail app's own browser, or once the session was gone, a guest had no way in. Asking a guest to invent a password would add a step for someone who chose not to have an account, and the email already proves what a password would: that they can read mail sent to that address. The code sits after a `#`, which a browser never sends to a web server, so it is not in the site's own logs or in a `Referer` header. (The page does send it to the database service, in the body of the calls it makes, which is how the database checks it.)

**How it was built:** Migration `20261026100000_booking_access_link.sql`. `booking_access_tokens` (booking, hash of the code, expiry) has row security on and no access for anyone. The code itself is never stored, only its SHA-256 hash, so nothing in the database can be turned back into a working link. `mint_booking_access_token` (the email sender only, with the service key) makes a code of 64 characters from two random UUIDs (about 244 bits), stores the hash, and tidies away codes that lapsed more than a week ago. `booking_link_client` (inside only, closed even to the service key) checks the booking, the code and the expiry, gives the same error for every kind of failure, and on success makes the rest of that one database call act as that client (the claims `sub` and `link_client` are set for that transaction only). Five functions are open to visitors and signed-in users: `booking_by_key`, `change_terms_by_key`, `availability_by_key`, `cancel_by_key` and `reschedule_by_key`. Each checks the code and then calls the existing signed-in function unchanged (`get_my_booking`, `get_my_change_terms`, `get_my_booking_availability`, `client_cancel_booking`, `client_reschedule_booking`), so the late fee, the notice, the availability and travel rules, the events, the emails and the Admin alert are the same code that runs for a signed-in client; the code only decides whose booking the call is for. `client_booking_for_change` and `get_my_booking`, the two the others use to find "my" booking, also accept the one booking a link has just proved, for the client it belongs to; a signed-in person cannot add those claims, because their claims come from their signed token. The proof names the booking as well as the client, and it lasts for one call: each of the five functions puts the caller back as they were (`booking_link_end`) as soon as its call has finished, so nothing later in the same transaction can go on acting as the client or reach their other bookings. In the sender, `withPrivateLink` asks for a fresh code just before a client email goes and puts `#key=<code>` on the link. It never saves the code in the delivery, the event or a log (it is also removed from any error text), and if a code cannot be made the plain link goes instead, so an email is never held back for it. The page (`AccountApp.jsx`, `accountApi.js`) reads the booking and the code, keeps the code for the tab in `sessionStorage`, removes `#key=…` from the address, calls the five functions, and ignores whoever happens to be signed in on that browser. It hides "Your bookings", offers "sign in" for the full list, and gives a link that does not work a heading and a plain message with no "Try again" (trying again cannot help). A visitor with no sign-in who opens an address without a code (an email sent before this change, or the calendar file) is told: "Booked as a guest? There is no password to enter. Use the link in your latest confirmation email, or the phone you booked on. If you have an account, sign in below." Someone signed in as a different person is told in plain words that the appointment is not on the account they are signed in to. There are no new settings: the sender already has the service key.

**How it was checked:** The database tests cover who can call what, that only a hash is stored, expiry and tidying, that every kind of bad code gets the identical answer, that the terms and times equal the signed-in ones, cancelling and moving by link (the same request key twice, the late-fee acknowledgement, a client with no login, another booking's code), that the person recorded as acting is the client even when someone else is signed in, that a code opens its own booking and not another booking of the same client or anyone else's, that the caller is themself again after each of the five calls, and that the signed-in rules did not change (96 checks). An integration test sends a real queued email, checks that the code in it opens the booking and a wrong one does not, and that the code is stored nowhere. Twelve browser tests open the link in a fresh browser, check that the code leaves the address bar, reload, use it for each kind of client and while signed in as the Admin or as the client themself, give a wrong and a lapsed code, cancel and move (with and without a late fee), take up a newer code opened in the same tab, cope with a browser that will not keep the code and with a full stop after the address, and check the layout at 390, 320 and 1280 pixels. Forty-six deliberate breaks of the database functions and permissions and twenty-four of the sender and page were applied one at a time and a test failed for every one; the ones that first slipped through (a signed-in person using someone else's link, an Admin email getting a code, and every break the independent review listed) now have tests. The accessibility checker found one problem, a missing page heading on the "link does not work" screen, which is fixed; the six screens are clean at all three sizes.

**Found by an independent review and fixed before release:** an existing test of the signed-in page still expected the old generic message for someone else's booking and would have failed (the whole suite had not been run yet); a link's proof covered every booking of its client, not only its own, so a code for one booking could in principle have been used on another booking of the same client whose number was known, if two calls ran in one database transaction (a request to the online project runs exactly one, because the GraphQL extension is not installed there, which was checked, but it is closed anyway: the proof now names the booking, and each call puts the caller back when it finishes); the sender made a code for any client message, including a Telegram one (which would show it in the text and on the button) and for an email with no public address to put it on; the page took the code out of the address even where the browser would not keep it, so a reload then failed; a full stop a mail app adds after the address spoiled the code; the screen for a link that does not work had no way to sign in; and the wording for someone else's booking still sent a guest "to the phone they booked on". Tests that could not have caught a break were added: a code for an appointment that has already happened must not be born lapsed (an email sent after the appointment, a refund for example), moving inside 24 hours must carry the fee that was acknowledged, the cancellation reason must be kept, one booking's code must not open another booking of the same client, the caller must be back as themself after each of the five calls, and the settings that make the proof last for one transaction only are checked in the definitions.

**Limits, on purpose:** Anyone with the email can manage that booking until 30 days after the appointment, and one link cannot be switched off on its own (a deleted booking takes its codes with it; a cancelled booking's link still opens and shows it cancelled). Emails sent before this change, and the link inside the "Add to calendar" file, keep the old address with no code: they open the booking only on the phone or browser where the client booked or signed in, and elsewhere the page explains what to do; the calendar file could be given a code in a later change. A new code is made for every email and earlier ones keep working until they lapse. A mail app that opens links in a full browser in the background could load the page and so read the booking, but it cannot change anything: that needs a tap and, inside 24 hours, a ticked late fee. Wrong codes are not counted or slowed down; at 244 bits guessing is not realistic, but failing calls can be made as often as Supabase lets any request be made. The sender and the website can go live before or after the database change with nothing breaking: until the change is applied online the sender cannot make a code, so emails keep the old link, as today. Something done through a link is recorded with the client's own number as the person acting (a signed-in client's is their sign-in number); both are recorded as "client", so the history cannot tell a link from a sign-in. A link visitor runs as the database's anonymous role, which gets a shorter time limit than a signed-in client (3 seconds against 8, the same online as here). A mail-security service that rewrites or scans links in email sees the whole address, code included, as it sees the whole email, and a browser's history can keep the address as it was first opened even though the page then takes the code out of the address bar.

## ADR-044 — A client is reminded by email on the morning of their appointment (2026-10-14)

**Decision:** On the morning of an appointment the client gets one reminder email: "Hi Ava, a quick reminder: your appointment is today at 14:30, at 12 Edith Road. I'm looking forward to seeing you! You can see or change your booking here: …", with the usual sign-off. Only confirmed appointments are reminded (not ones waiting for payment or cash approval, and not cancelled ones), only when the booking has an email address, from 08:00 London time, and only when the appointment is at least an hour away. A client who was already emailed about that booking earlier the same day (booked, confirmed or moved) is not reminded as well. The owner chose the morning of the day only (no evening-before and no hours-before), the wording above, and email first, with Telegram to follow.

It writes the reminder as an ordinary client email in the notification queue and records it as an event with a deduplication key (booking and date), so running it again, or twice at once, never repeats a reminder. Sender tests cover the new step, its failure, and the rounds.

A booking made or changed later the same day is told about in its own email, so it gets no reminder. Reminders cannot be turned off for one client, and there is no evening-before reminder. ## ADR-045 — A first appointment that nobody has booked can be released (2026-10-14)

**Decision:** A first appointment set to **At a set time** can now have a **release time**. If nobody has booked that first appointment by the release time on the day before (London time), an empty day is offered as **Any time in my hours** from then on: every usual time between the day's start and end, instead of only the first appointment. It is set where the first appointment is set, on each weekday of the usual week and on a special day, as "Keep it until someone books" (the default, which changes nothing) or a half-hour time "the day before", for example 17:00 the day before. A special day has its own release time (or none) and does not borrow the usual week's, in the same way that it replaces the usual week's hours. A day with **Any time in my hours**, and a day off, have no release time. Once someone has booked, the day is built around the bookings as before, release time or not; if that booking is cancelled and nobody else has booked, a day already past its release time is open again. The owner chose that the release time counts from the day before (for example 17:00 the day before), and asked for it as part of the Day settings work. It is built first because the Day settings panel will need it to exist.

**Reason:** With a first appointment at a set time, an empty day offers clients only that time. If nobody books it, a client who looks later sees no times at all once that time has passed, or is inside the notice period, even though the day has hours left (ADR-039 lists this as a known limit). Nothing in the app could release a first appointment, and the owner's design for the Day settings panel includes a release time.

**How it was built:** One database change, `20261030100000_anchor_release.sql`: a nullable `anchor_release_minutes` (0 to 1439) on `working_hours` and on `working_hours_overrides`, allowed only with a first appointment at a set time, and one new rule in `compute_booking_availability`, the single function that the booking page, holds, rescheduling and the Admin's list of usual times all use. On a day with no bookings and a set first appointment, if "now" is at or after the release time on the previous date (London time), the first appointment is not applied. The function's signature and every other rule are unchanged, and the notice period and how far ahead clients may book are still applied outside it, as before. The reference engine in `schedulingEngine.js`, which the parity tests use, has the same rule (`anchorReleaseInstant`, which stays right either side of the clocks changing). Database tests (`anchor_release.test.sql`, 27 checks) cover the minute before and the minute of release, overnight and on the day itself, a booking making the day a chain, a cancelled booking, blocked time, no release time, "Any time in my hours", a special day replacing the usual week's release, both clock changes, and what the tables accept; nine of them fail without the new rule. Unit tests cover the screen's rules, what is sent to the database and that the release time is read back (so saving a day never wipes one the screen did not show). Browser tests cover setting it on the usual week and on a special day, dropping it, and the client page: a day already past its release time offers every usual time, one that is not yet released offers only its first appointment, and no release time behaves as before.

**Limits, on purpose:** The release time is always a time on the day before; there is no "same morning" choice and no release for one booking. It is counted in London time and applies only to a day with no bookings. The Calendar and Agenda do not show it yet (the Day settings panel will). The database change had to be applied online before this was deployed, because the Working hours screens read and save the new column; it was safe to apply first, since nothing changes until a release time is set. It was applied to the online project on 2026-10-15 and checked there read-only.

## ADR-046 — A day can be Chain or Flexible (2026-10-14)

**Decision:** Each day has a **schedule mode**: **Chain** (what every day has always been, and still the default) or **Flexible**. Once a day has appointments, a Chain day offers only the two ends of the day's run, and a Flexible day offers every half-hour start in the working hours that leaves room for the travel time on both sides of every other appointment, gaps between appointments included. An empty day is the same in both: its first appointment (and release time) decides what it offers. The mode is set in the same places as the hours, on each weekday of the usual week and on each special day, which starts from the usual week's mode and has its own from then on. The owner defined Flexible this way, chose Chain as the default, and asked for the mode to be set on the usual week, on a special day and, when it exists, in the Day settings panel.

**Reason:** The owner's design for the Day settings panel includes a schedule mode, with Flexible meaning availability worked out "more freely across the working hours". Until now the app had one way of filling a day, the chain (described in `docs/HOW_TIMES_ARE_OFFERED.md`), so a gap between two bookings could never be offered however big it was.

**How it was built:** One database change, `20261031100000_schedule_mode.sql`: a `schedule_mode` column (`chain` or `flexible`, default `chain`) on `working_hours` and on `working_hours_overrides`, and one new branch in `compute_booking_availability`, the single function that the booking page, holds, rescheduling and the Admin's list of usual times all use. For a flexible day with appointments it offers each half-hour start with room for travel on both sides of every appointment (a time a client is holding counts as one, and a booking that is being moved is left out). Blocked time follows the checks that the two ends of a chain already had: it may not overlap the treatment, or the travel into it from the appointment before it, or, for a new first appointment, the travel on to the next one. That makes a flexible day always offer everything the same chain day would, which the tests check. The reference engine in `schedulingEngine.js` has the same rule. Database tests (`schedule_mode.test.sql`, 34 checks) cover the gaps, an exact fit, holds and moves, blocked time next to travel, the first appointment on an empty day, a shorter travel time, the usual week against a special day, and what the tables accept; they fail when the rule is removed or either blocked-time check is left out. The database function and the reference engine were also compared over about 2,000 generated scenarios (bookings, blocked time, treatment lengths, travel times, both modes, with and without a first appointment) with no differences. Unit tests cover the engine, what the screen sends and that the mode is read back, and browser tests cover the Admin screens and the client page: a chain day with a booking at 15:00 shows two times and the same day set to flexible shows every time with room for travel.

**Limits, on purpose:** Times are on the half hour; a booking made at some other minute leaves the next half hour after its travel time. A flexible day does not move existing bookings or fill gaps for you; it only makes more times available to clients. The travel time is the one hour it always was. The Calendar and Agenda do not show the mode yet (the Day settings panel will). The database change had to be applied online before this was deployed, after the release-time one, because the Working hours screens read and save the new column; it was safe to apply first, since every day stays Chain. It was applied to the online project on 2026-10-15 and checked there read-only.

## ADR-047 — Day settings: one date on its own, from the Agenda or the Day view (2026-10-14)

**Decision:** Every day in the Agenda has a visible **Day settings** button, and so has the Day view (beside Block time). With Show every day on, each free day's whole line opens it, and a **Day settings for a date** button beside that switch opens any date, with or without bookings, whether or not the Agenda lists it. It opens a page for that date, with the date in its address so Back and bookmarks work. The page shows, in this order: a one-line summary of the day (hours, Chain or Flexible, first appointment and when it is released), how many bookings run from when to when, and whether the day follows the usual week or is a special day; **Hours and schedule** (working day, start and end, schedule mode, first appointment and its release time, a note), saved together with one **Save this day** button; **Blocked time** on that date, which can be changed, removed or added to; and the day's **Bookings**, each opening as it does everywhere else. **Use my usual week** puts the date back, after asking, because it removes the date's own settings (the question names what the date goes back to and starts on "Keep this day's settings"). The warning about a booking left outside the new hours says what the new hours are and the whole time of each booking. What is saved is a special day, the same record the Special days list shows, so the date changes and the usual week does not. The owner asked for this with a screenshot and a written spec, and chose a visible button, one Save button, and that the release time and Flexible mode can be set here as well as on the usual week and special days.

**Reason:** The owner wanted to press any day in the Agenda or the Day view and adjust just that date, instead of going to More, Working hours, Special days, adding the date and choosing its hours.

**How it was built:** No database change of its own. `DaySettings.jsx`, a lazily loaded screen at `/admin/day-settings?date=…`, reads the date the way the Day view does (one read of its hours, special day, blocks and bookings) and saves with the same `saveOverride` and clash check as Special days. The hours fields are now one shared component (`HoursFields.jsx`), so a day is edited in the same words everywhere. The pure parts (what a date holds, the two summary lines, whether anything changed, which changes can strand a booking) are in `daySettings.js` with unit tests. The clash warning appears only when the working hours themselves change, because a different schedule mode or first appointment moves nobody, and it counts only a booking that is itself in the time that stops being working time, not the travel around it (the database counts an hour of travel either side of every booking, which is right for blocked time but wrongly warned about the first booking of a day that starts as the hours do; the fix is shared with the Special days screen). A day that has passed can be looked at but not changed. The heading takes focus itself once the page has appeared: the Admin's own move of focus to a new page's heading can land on the page being replaced, which stays in place, hidden, while a lazily loaded page arrives. Browser tests cover opening from the Agenda, the Day view and a free day; the summary; saving everything with one button and seeing it in the Agenda and the Special days list; the clash warning once, never moving a booking; a day off, back on and back to the usual week; a mistake in the hours; blocked time added, changed and removed; bookings listed and opened; a passed day; an address that is not a date; and a 320 pixel phone.

**Limits, on purpose:** The Agenda lists only days that have bookings, a special day, blocked time or time away (and today), unless Show every day is on, so a free day is reached from there with the date button or with Show every day. The first day of a stretch of time away is stood for by its banner, which opens the block, so its settings are reached with the date button or the Day view. It reads with `select('*')`, so it opens even before the release-time and schedule-mode database changes are applied online, but saving a day writes those columns, so both migrations had to be applied online first, as for Working hours. Both were applied on 2026-10-15. Blocked time keeps its own dialog and its own save, so it is not part of the one button. There is no warning when leaving with unsaved changes; a line on the page says so. The Agenda's special-day notes do not yet mention "flexible" or the release time, because the Agenda is the home screen and must not depend on columns that may not be online yet.

## ADR-048 — "Not yet": a payment you cannot settle yet can be put off, and the Agenda's cards, headings and Needs you box are thinner (2026-10-15)

**Decision:** A payment that needs the Admin (a bank transfer the client says is paid, or a cash request) has a **Not yet** button beside Verify or Approve, in the Needs you box and on the To check page. It asks when to be reminded (in 3 hours, tomorrow at 09:00, or 09:00 the day before the appointment, London time; only times that are still ahead and never after the appointment has started, and a short one when the appointment is close) and sets nothing else: the booking keeps its time, the client is told nothing, and no booking, payment or message is changed. The payment leaves the Needs you box and the number on To check, and waits on the To check page as "Reminder set · back tomorrow, 09:00" with **Check now** to bring it back at once (and Undo in the message that appears). It comes back by itself when its time comes, and at once if the booking or its payment changes (the client declaring again, say). It is a reminder inside the app, shown the next time the Admin opens it; it does not send the Admin a message. It never cancels or confirms anything. ADR-019 still holds: nothing is cancelled automatically.

**Reason:** The owner could not settle some payments yet (a transfer the client says is made but has not reached the bank, for instance) and the box kept asking. The owner first suggested a dismiss; a plain dismiss could hide an unpaid booking that is holding a time, so it is a reminder that always returns. The owner's answers: remember it on this phone only, no database change.

**How it was built:** `paymentReminders.js` keeps the reminders in this browser (`localStorage`, key `vad-admin-payment-reminders`), one entry per booking with the time it is due and a fingerprint of the booking's and payment's `updated_at`; a screen that shows payments reads them through `useReminders`, so putting one off changes the box, the number and the To check page together. If the device cannot keep them, they last for the visit; if it forgets them, the payment simply comes back, which is the safe way to be wrong. `summariseToCheck` counts a payment that is put off apart from the ones that need the Admin. No database change and no new package.

**Also in this change (the owner's picks after trying the preview):** booking cards use the full width with their time inside (the left column of times is gone), slightly thinner (a normal card 122px, was 148px); each Agenda day's heading is one line with an icon-only Day settings button (44 by 44, named for screen readers), so the heading that stays pinned while scrolling takes 48px instead of 102px, and the special-hours or time-away note sits in a slim strip under it; the Needs you box is one line of heading and a row per payment, about a third shorter. An appointment's end on its card is its start plus the treatment's own length, never the travel time.

**Limits, on purpose:** Reminders are not shared between devices (a laptop shows the payment as needing the Admin until it is put off there too). Nothing buzzes the phone; a Telegram or email nudge would need the reminders kept in the database and a scheduled job, and can be added later as an explicit change.

## ADR-049 — A client can get their booking updates on Telegram, from a bot of their own (2026-10-13)

**Decision:** The confirmation page (a booking that is confirmed, or is waiting for Vad to check the payment) has a box at the top: **Get updates on Telegram**. The same box is at the top of an open booking on the "Your appointment" page, so a client who has closed the confirmation can still find it, and can switch updates back on after sending /stop. One button, **Open Telegram**, opens a new bot that is only for clients; pressing Start there links that chat to the client, and the bot answers "You're connected, <first name>", with a way to stop if that is not them. From then on every email the app sends that client about a booking (confirmed or payment received, moved, cancelled, refund sent, and a booking the Admin made for them) is also sent to that chat, in the same words. The page notices by itself when the chat is linked and says so ("You're connected on Telegram"). **/stop** in the chat ends it and drops whatever was still waiting to be sent to that chat, and so does blocking the bot. The bot answers anything else with where to change or cancel (the link in the email, or Vad), and reads nothing else. A guest who booked without an account can do all of it: the box works for whoever's booking it is. Nothing is sent to a client who has not linked a chat. The box is only shown when the bot is set up: if the site has no bot name, or the database does not answer, the client sees nothing at all, never an error.

The Telegram message has no link to the booking page (a private link in an email must never be copied into a chat), and a message about a booking being made, confirmed or moved ends "To change or cancel, use the link in your email, or contact Vad." Receipts and the reminders for repeating bookings are not sent to Telegram. The Admin's own alerts are unchanged and still go to the Admin's chat from the Admin's own bot; client messages go out on a channel of their own with the clients-only bot, and the two can never be mixed up.

**Reason:** The Admin asked for it ("Confirmation page of clients booking should have a Telegram box on top, so they can press it and receive notifications by telegram") and chose a new bot just for clients, so the Admin's own Telegram alerts are not disturbed and a client's chat can never be the Admin's chat.

**How it was built:** Migration `20261028100000_client_telegram.sql`. `client_telegram_tokens` holds the one-time codes (random, 32 characters, only the hash is kept, valid for two hours, used once, at most ten an hour per client), and `client_telegram_links` the linked chats (the chat number only: no name or username is kept; a client's rows go when the client is deleted). Both have row security on and no access for anyone from outside. A signed-in client or a guest asks for a code with `create_my_telegram_link` and asks whether a chat is linked with `my_telegram_status`; both answer only for the client behind the session. Only the Telegram webhook, with the service key, can link or stop a chat (`link_client_telegram`, `stop_client_telegram`): linking answers "linked" (with the client's first name, on one line and at most 40 characters), "used", "expired" or "invalid" so the bot can reply kindly, and asking again for a chat that is already linked still says "linked", so a retry from Telegram cannot turn a success into "already used". Linking a chat also spends the client's other unused codes. Stopping a chat marks the messages still waiting for it as failed (as stopping a receipt email does), so they are not sent. The messages are not written a second time: a trigger on `notification_deliveries` copies each client email about a booking (an allowed list of booking events only) to every active chat of that client, without the line pointing at the booking page and the sign-off. So whatever sends no email sends nothing there either, and the notification planner was not touched. When two client profiles are combined ("same person"), a trigger just before the emptied profile is deleted moves its chats to the profile that stays. The channel check on deliveries gained `telegram_client`, allowed for clients only. `server/notifications.js` sends those rows with the clients-only bot token to the chat number, refuses to send an Admin message to a client chat or a client message to the Admin chat, ignores a clients-only token that is the same as the Admin bot's, cuts a call to Telegram off after eight seconds, and ends the link of a chat Telegram says has blocked the bot or does not exist, so nothing more is queued for it; failures are retried like emails and the token is scrubbed from any error. `api/telegram-webhook.js` (a second serverless function) refuses any call without Telegram's secret (compared in constant time; trimmed, and at least 16 characters) before reading it, ignores groups, channels and edits, answers Telegram "ok" unless our side failed (so Telegram retries only then), and never returns details. The page side is `TelegramBox.jsx` with `telegramApi.js` and `telegramLink.js` (the bot link, when to replace a code, and looking again for a few minutes after the button is pressed), shown from `ConfirmationStep.jsx` and `AccountApp.jsx`.

**Found by an independent review, and fixed:** A reviewer who had not seen my reasoning read the migration, webhook, sender and screens and queried the local database. No way to read or link another client's data was found. It found, and I fixed: the box was only on the confirmation page, which a closed tab never shows again, although the bot told people to open their booking page (it is now on the booking page too); combining two profiles silently dropped a linked chat; /stop did not stop messages already queued (a confirmation queued just before could still arrive after "I won't send you any more"); the bot's answer did not say whose appointments a chat had been connected to, so someone sent a client's button address would not notice; the client's other codes stayed usable after one was used; calls to Telegram had no time limit; the closing "To change or cancel" line was also on cancellations and refunds; the box looked for the client pressing Start for only five minutes after it appeared, not after the button was pressed; the setup guide did not say that every setting needs a redeploy, that the bot name should be set last, or that the address with the secrets is best opened in a private window; a secret pasted with a trailing line break would have refused every call, and the Admin bot's token could have been entered for the clients' bot (a short secret and the same token are now refused, and values are trimmed).

**What only the owner can do:** make the bot in BotFather and tell me only its username; put three settings into Vercel (`TELEGRAM_CLIENT_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, and last `VITE_TELEGRAM_CLIENT_BOT_USERNAME`) and redeploy after changing them; and open one web address once so Telegram knows where to send messages (steps in `docs/NOTIFICATIONS_SETUP.md`). Nothing works until then, and the box stays hidden.

**Limits, on purpose:** The code in the button's address is good for two hours and one use (and linking spends the client's other codes); someone who could see the client's screen in that time could link their own chat and would then get that client's appointment updates (the same things the email says). Anyone who is *sent* a client's button address and presses Start gets that client's updates in their chat: the bot's answer names the client, so it is plain that it is not them, and /stop ends it. Messages say what the email says, including the address, and Telegram keeps its chats on its own servers; the client chooses to link. There are no reminders yet, no Telegram receipts, and the Admin's screens do not show who has linked a chat. The bot does not read replies, so a client who types "can I move it to Friday?" is pointed to the email link and to Vad. A chat that blocks the bot is only found out when the next message is sent. A failed message is tried again up to five times, like an email, and a message that is being handed to Telegram at the very moment of /stop is still delivered. The existing senders for the Admin's Telegram and for email have no time limit on their calls, as before. The box appears a moment after the page, once the database has answered, so the page below it moves down when it does. The database change is not applied to the online project yet.

## ADR-050 — The Agenda leaves out cancelled bookings unless asked (2026-10-15)

**Decision:** The Agenda, the Day view and a day's own page no longer list cancelled bookings by default. A second switch, **Show cancelled**, sits on one line with **Show every day** and brings them back; it is off until it is switched on, and is kept on the device like the first. A day with only cancelled bookings is not on the Agenda unless the switch is on (today always is). One exception: a cancelled booking with money still to sort out stays listed whatever the switch says. That means a refund still to send (only once the payment was received, the condition that offers Record refund) or a late fee still due. Its status is in the amber of things that need the Admin ("Cancelled · refund £85.00 to send", "Cancelled · late fee £85.00 due", or both), on a card that stays the grey of a cancelled one, and it drops out of the list when the refund is recorded or the fee is received or waived. The Day view and a day's own page have no switch of their own: they follow the same choice, and a day that has cancelled bookings has one line there, "Show 2 cancelled bookings", which becomes "Hide cancelled bookings" once they are on show. The two switches are on one line even on a 320px phone (a little smaller there), and the **Day settings for a date** button has the line above them.

**Reason:** The Admin asked for the Agenda to show only current bookings, with the cancelled ones and the empty days both one switch away. Two switches rather than one because the two jobs differ: empty days are for planning (finding a free day), cancelled bookings are for looking back, and a single switch would bring in every empty day just to see what was cancelled. "Show cancelled" is the wording that fits the smallest phone on one line. The exception is there because nothing else lists refunds to send: the cancellation alert says so once, and the booking's own page shows "Refund due"; hiding a cancelled booking outright could hide an unsent refund.

**How it was built:** `src/admin/cancelledBookings.js` holds the rules (`moneyToSort`, `listedBookings`, `useShowCancelled`, kept under `vad-admin-agenda-show-cancelled`). The Agenda filters its bookings before it builds its days, so a day left with nothing drops out. The Day view filters before it builds its timeline, so a day's free time reads as one stretch. `BookingCard` names the money, and `CancelledToggle` is the one line in the Day view and on a day's own page. No database change and no new package. Tests: `cancelledBookings.test.js`, and six browser tests in `adminCancelledSwitch.spec.js`; the older browser tests that are about the cards ask for cancelled bookings to be listed, since the default is now to leave them out.

**Limits, on purpose:** The choice is per device (the Agenda's other switch is too). Day headings count what is going ahead, as before. Clients, Alerts and To check are unchanged and still show cancelled bookings. No-shows and finished appointments are not cancelled, so they stay listed. Cancelled bookings are only hidden from view, never changed.

## ADR-051 — A client who forgets their password gets a page of their own for it (2026-10-16)

**Decision:** The link in a client's password reset email opens one page, `/reset-password`, whichever page the reset was asked for from. It shows **Choose a new password** at the top, asks for it twice (at least 8 characters), saves it, and leaves the client signed in, with ways on to Your bookings and to book. It works only for the session the link itself made: someone who is simply signed in cannot use it, and opened with no link it shows no form. A link that was used already or has run out, and the page opened with no link, say so in words and offer to send a new one from the same page, in the same words whether or not there is an account for that email. When any email link brings someone back to the booking page or Your bookings with a problem (used, expired), those pages now say so in plain words, and tidy the address, instead of opening as if nothing had happened.

**Reason:** The owner tried it on the live site on 2026-10-16. The link signed them in on the booking page's first step, with the new-password form at the very bottom of that page; from Your bookings it signed them in without ever asking for a new password; and a second press of the link, which they made because nothing seemed to have happened, opened the page as normal and said nothing about the "expired" error that was only in the address bar. Supabase's sign-in log showed the first press logging in and the second being refused, and the same three behaviours were reproduced locally. No database change and no new package. Tests: unit tests for the three small modules, and ten browser tests in `clientPasswordReset.spec.js` that use real links from the local sign-in service (a fresh link, the old password refused, a used link, no link, signed in but no link, both Forgot password? forms, older links, a bad email link, the smallest phone and the keyboard, and the wording for too many requests).

**Limits, on purpose:** A link works once, and stops working after a while (Supabase's rule, not ours); a mail program that opens links to check them can use one up, and the page then offers a new link. After a password is saved other devices stay signed in. The Redirect URLs in Supabase must allow the page: `https://booking.vadmassage.com/**` covers it, and the booking page, Your bookings and the Admin's reset page. The Admin's own reset page is separate and unchanged.

## ADR-052 — Your bookings says where each booking's money stands (2026-10-16)

**Decision:** Each booking in a client's Your bookings list has one quiet line under its treatment that says where its money stands: "£90.00 · Paid"; "£125.00 · Pay in cash at your appointment" for a cash booking still to come (once it has passed it says "£125.00 · Cash", and "Paid" after the Admin records the cash as received); "£90.00 to pay by bank transfer"; just "£90.00" once the transfer has been sent; "Refund of £90.00 on its way" and then "Refunded"; and "Late fee of £90.00 due". **Decision:** On the Admin's cards (the Agenda, the Day view and a day's own page), a cancelled booking says who cancelled it and when, after its status: "Cancelled" and then "by client · Wed 14 Oct, 18:20", "by you", or "automatically". When the status is long (money still to send) the note drops to a line of its own, so the cards stay as narrow as they were. ## ADR-054 — One look for the whole app: ivory, slate blue and midnight navy (2026-10-16)

## ADR-055 — Emails to clients come in the look of the booking pages, beside the plain text (2026-10-17)

**Decision:** Every email a client gets (booked, confirmed, moved, cancelled, refunded, the morning reminder, a receipt) is sent as both plain text and an HTML version in the look of the booking pages: "VadMassage" in the serif at the top, the title with its last word in slate-blue italics, the words of the message, the day and time in bold, the booking reference small, a slate-blue button "See or change your booking" holding the private link in place of the long link, and a quiet footer (a line inviting a reply, what to do if it landed in spam, and the tagline). The sign-in and reset emails that Supabase sends are separate and keep their own templates. The look in Gmail, Outlook and Apple Mail varies a little (rounded corners are square in some versions of Outlook); the layout uses tables and inline styles so it holds everywhere.

## ADR-056 — A client needs only a name (2026-10-17)

**Decision:** The Admin can add a client with only a first name. The last name, phone, email and address are all optional. A phone or email that is given still has to look right and still cannot belong to another client. An address is optional as a whole: leave it out, or give the street, city and postcode (a bare city, which the screens fill in as London, does not count as an address). Editing a client follows the same rule, so contact details can be left empty or cleared. This replaces the part of ADR-025 that said new clients are added with an address, and the old rule that every client needed a phone or an email.

**Reason:** The owner asked for it on 2026-10-17, just before importing her real clients: often only a name is known, or a name and an address. The database never needed more (`clients` has only a name that must not be blank), only the Admin's commands and screens insisted.

**How it was built:** Migration `20261101100000_client_name_only.sql` replaces `admin_create_client` and `admin_update_client`: the "an email or phone is required" check is gone, a start on an address needs all of street, city and postcode, and no address row is made when none was given. Nothing else in them changed (the duplicate checks, the request key that makes a retry safe, the `client.created` event, who may call them). It is safe to apply before the screens change. The two forms that add a client (Clients, "+ Add client", and New booking, "+ Add new client") and the checks in `src/admin/clientsApi.js` follow the same rules, and the profile no longer shows an empty "Quick contact" row for a client with nothing to call or email.

**Limits, on purpose:** Two clients with the same name and nothing else are two clients: a name is not an identity, so the Admin chooses carefully (no warning is shown). A client with no email is sent no emails and nothing is queued for them. A booking for a client with no saved address still needs an address typed for that appointment, as for any one-off address. Nothing here changes how clients add themselves or how guests book.

## ADR-057 — The Admin can record an appointment that has already happened (2026-10-13)

**Decision:** New booking has a box, **It has already happened**. Ticked, the day picker is replaced by "Day it happened" (any day in the last year, up to today, named in full with its year) and every half hour of that day that has begun, from 06:00 to the last start that finishes by midnight, with what was in the diary that day. It looks and works like the usual picker. Working hours, the usual 60 minute gap and blocked time are not applied to something that has happened: the only time that is refused is one that overlaps another appointment (greyed, and tapping it says what it clashes with). Payment becomes **Paid by bank transfer**, **Paid in cash**, **Not paid yet — bank transfer** or **Not paid yet — cash** (the last two say how the payment will come, so that when it does it is recorded as what it was). A paid appointment is recorded as **completed** straight away: it counts as a visit and in what the client has paid, it can have a receipt, and its history shows it made confirmed and then completed. Its payment is dated the day and time of the appointment (never later than now), so a receipt reads "Paid by … on <the day of the appointment>"; her own check of it is dated when she recorded it. Completed is final from this screen (it cannot be cancelled or changed from here afterwards), so she is asked once more before a paid one is recorded, with the client, the day with its year, the time, the amount and how it was paid in front of her. One that is not paid yet stays **confirmed**, with no question, and she finishes it like any appointment that has started (receive the payment, complete it). **The client is never emailed about it**, and nobody is alerted: they were there. That holds for what happens to it afterwards while it is still in the past too (cancelling it again, a payment arriving later); moved to a time still to come, it is announced like any appointment. It is never the start of a repeating booking. It is a deliberate act: the request has to say "past", and without it a time that has begun is refused exactly as before, so a form left open cannot record one by accident. Opening New booking from a day that has gone (from the calendar) starts with the box ticked for that day, and the box turned off goes back to today.

**Reason:** She asked for it ("I should be able as an admin to create bookings in the past times") and chose: completed when it is paid and no email; an unpaid one stays confirmed; a window of about a year back. The client was there; telling them about it afterwards would be noise (and "your appointment is booked" for last Tuesday would be wrong).

**How it was built:** Migration `20261027100000_admin_past_bookings.sql`. `admin_past_booking_times(date, minutes)` is new (Admin only, the same shape as `admin_booking_times` but for days that have gone: nothing is "usual", overlaps are marked, a client who is part-way through booking is flagged, and today lists only times that have begun). `admin_create_booking` takes an optional `past` (yes or no; not together with `any_time`). In that branch the time must have begun (London time) and be no more than 365 days back, must not run past midnight or overlap another appointment (`admin_time_clash`), and waits while a client is part-way through booking that day (as unusual times do). The booking is made confirmed as always, and a paid one is then moved to completed through the one step the status guard allows (confirmed to completed), with a `booking.completed` event like the normal completion; its payment gets the appointment's day and time as `paid_at`. The `booking.created` event carries `past: true`. In `plan_event_notifications` one block was added after the messages are worked out: a client message is dropped when the booking's start has already begun and its `booking.created` event says `past` (the function was re-created whole from its newest definition; that block is the only difference, checked line by line). `admin_create_series` refuses `past`. The screens are the new `PastTimes.jsx`, the box and the payment and summary wording in `BookingSteps.jsx`, the question and the wiring in `AdminNewBooking.jsx`, the draft field in `adminBookingDraft.js`, and `newBookingApi.js`. The day picker clients use was not touched.

**Changed after two independent reviews and further checks:** Cash still to be paid was first refused for these, which would have made a regular who pays cash be recorded as a bank transfer; it is now a choice of its own ("Not paid yet — cash"). The client was first spared only the first email; the later ones (a cancellation, a payment) would still have reached someone who never knew of the appointment, so the quiet rule now covers everything while the appointment is still in the past. A paid one was final with no second look, so the question was added. The day is shown with its year in the picker, the question and the summary. A time chosen for the future is not carried over to the day that has gone. A draft kept from before the box existed follows its own day, not the day New booking was opened from, and a half-made draft with nothing in it worth keeping (only a day or a time was touched) is not brought back at all, because it could bring the box back, ticked, for an old day. While a client is part-way through booking today the screen says so, instead of failing. If the website is ahead of the database she is told in words that it is not ready yet, not shown a field name or a code. A weekly repeat left switched on in an older saved draft is switched off when that draft comes back as something that has already happened, and the note about a time that overlaps no longer follows her to another day. The second review also changed how a paid one is dated (the day of the appointment, not the day it was recorded, so a receipt reads right) and a database test that failed every evening between 22:30 and midnight.

**Limits, on purpose:** The booking's reference and "made on" time are the day she records it. The price is today's price list, even for an appointment in the past, and a completed one cannot be corrected from the app. A paid one makes a new client a returning client (they may then hold up to five upcoming bookings, and "your first appointment is already reserved" no longer applies), which is true of them; a client with an account sees it under Earlier in their bookings. A repeat is not available for these. A recorded appointment is not announced to the client, so if they want something in writing she sends a receipt. A completed appointment cannot be cancelled or changed from the app, so the question before a paid one is recorded is the safety net for the wrong client or the wrong day; one that is not paid yet can still be cancelled. Recording an appointment from earlier today counts, when the times offered to clients are worked out, like any earlier appointment that day: the times are measured from the last appointment of the day, so afterwards clients are usually offered only the time an hour after it (and the one before the first, which has usually gone), and most of the rest of today is closed to online booking. The question before a paid one is the browser's own question box, as for discarding a booking; a browser that has been told to stop showing those makes Record booking do nothing for a paid one. The sticky Record booking bar covers part of a long list of times at one scroll position, as the Create booking bar always did, so an accessibility checker can flag a time under it there (reaching a time by keyboard keeps it clear of the bar). The database change is not applied to the online project yet: until it is, the box says that recording is not ready yet and nothing is saved. It is numbered after the private-link change (`20261026`), which is not online either: apply them in order, or with `--include-all` after a dry run (neither depends on the other), and compare the online `plan_event_notifications` with the `20261017100000` text first, because this migration replaces it whole.

**If it ever has to be taken back:** run the previous definitions again (`admin_create_booking` and `admin_create_series` from `20261024100000_admin_any_time.sql`, `plan_event_notifications` from `20261017100000_booking_rules_settings.sql`) and drop `admin_past_booking_times(date, integer)`. Appointments already recorded stay as they are: they are ordinary bookings.

## ADR-058 — A booking can repeat in more ways, and what is coming can be cancelled from the repeat (2026-10-18)

**Decision:** ADR-030's repeat was "every <weekday>". It can now also be every 2, 3 or 4 weeks (any gap from 1 to 12 weeks, counted from the first booking), every month on the same weekday (the first, second, third or fourth Thursday, or the last one, taken from the date of the first booking), or on dates chosen one by one on a calendar (up to 59 after the first booking, within three years, with no end date: the last chosen date ends the repeat). Everything else about a repeat is as ADR-030 describes: one standing rule that keeps the slot free, a real booking made about a week before each date, nothing cancelled for the Admin. From the client's page the Admin can cancel some dates (a date that has a booking cancels that booking, a date that is only being kept free is skipped) or everything still to come, which also ends the repeat. "Stop repeating" is still there and leaves the bookings already made.

**Reason:** The owner asked ("weekly, monthly or every two or three weeks, or custom", "with an option to delete all upcoming bookings or only certain dates") and chose in a questionnaire: monthly means the same weekday each month (and "every 4 weeks" is its own choice), custom means picking the exact dates on a calendar, and the Admin's side comes first. Letting chosen clients make a repeat themselves is the next piece and is not built yet.

**How it was built:** Migration `20261103100000_repeat_patterns.sql`. `booking_series` gets `pattern` (weeks, monthly or dates), `every_weeks`, `month_week` (1 to 4, or 5 for the last) and `custom_dates`, with a check that the combination makes sense; every repeat made before is "every week". One function, `series_dates(series, from, to)`, says which dates a repeat has, and the holds, the daily job and the client's list all use it instead of each knowing "every weekday". `admin_create_series` takes an optional pattern (nothing sent means every week, so the old call still works), and a pattern that is wrong makes nothing, not even the first booking. `admin_client_series` lists the next twelve dates with their state (booked, with its booking; skipped, with why; paused; or kept free) and how many bookings are still to come. Cancelling is `admin_series_cancel_dates` and `admin_series_cancel_all_upcoming`: each booking is cancelled exactly as an Admin cancellation is (no late fee, a booking that was paid becomes a refund to send, the client is emailed, the cancellation recorded once), with a request key so a retry changes nothing; both refuse a repeat that has ended. Skipping a date now refuses a date that is not one of the repeat's. New booking has a Repeat box with the choice of how often and a month calendar for chosen dates; the client's page has Coming up with tick boxes, **Cancel selected dates** and **Cancel all upcoming**, each asking first.

**Limits, on purpose:** The time, length, address and payment way are the first booking's, for every date. Changing a repeat (its gap or its weekday) is done by stopping it and making a new one. "Every month" from a fifth Thursday means the last Thursday. A booking that has already begun is left alone by "cancel all upcoming". The first six of the next twelve dates are shown on the client's page and the other six are one tap away; dates further ahead are still kept free or skipped, but not listed. Clients cannot make or change repeats yet.

**If it ever has to be taken back:** run the previous definitions again (`refresh_series_holds`, `run_series_maintenance`, `admin_client_series` and `admin_skip_series_date` from `20261020100000_repeating_bookings.sql`, and the three-argument `admin_create_series` from `20261027100000_admin_past_bookings.sql`), drop `series_dates`, `series_cancel_dates`, `admin_series_cancel_dates` and `admin_series_cancel_all_upcoming`, and drop the four new columns of `booking_series` once no repeat uses anything but every week.

## ADR-059 — An address is one box of text (2026-10-19)

**Decision:** Wherever an address is typed there is now one box, **Address**: the client's details step, the Admin's **Add client** form and **+ Add address** on a client's page, and the one-off address on New booking. A whole address can be pasted into it in one go. It is stored as one text: `client_addresses.address` for a saved address and `bookings.address_snapshot` for the address a booking was made for (as it was on the day, like the other snapshots). Line breaks become commas, runs of spaces and doubled commas become one, and the text must be 1 to 400 characters. Entry instructions and a saved address's label stay as the separate small boxes they were. A postcode is no longer required or checked: an address with none gets a gentle note on the screen ("I can't see a postcode in that address…") and goes on, because only the person writing it knows whether it is complete. Two saved addresses count as the same address when their letters and digits are the same, whatever the spacing, commas or capitals, so the same address is not saved twice.

**Reason:** The owner asked for one single text box for the full address, on both the Admin's Create new client form and the client's self-registration form, so a whole address can be pasted in one go, with the data model changed to match and every existing address moved into the new field so nothing is lost. Four boxes (street, flat or building, city, postcode) made a pasted address land in the wrong one, and a made-up postcode check turned away real addresses.

**How it was built:** In two steps, so that nothing breaks while the two halves (the database and the website) are updated at different moments. Step one is migration `20261104100000_single_address.sql`. It adds the new columns and moves every address that exists into them (the four parts put together with commas, empty parts left out, for example `12 Garden Road, Flat 2, London, SW1A 2AA`); makes the four old columns optional; and teaches the database to accept an address either way. `clean_address(text)` does the tidying. A trigger on `client_addresses` fills the one text from the four parts when only the parts are written (an old screen), and clears the parts when only the text changes (a new screen), and keeps `normalized_address`, the lower-case letters and digits used to tell whether an address is already saved, in step with it; a trigger on `bookings` does the same for the snapshot. `finalize_client_booking` takes the address as a sixteenth, optional, argument; `admin_create_client` and `admin_create_booking` accept an `address` text; and everything that shows an address (the booking the client sees, the emails and Telegram messages, the morning reminders, the repeat reminders, combining two clients) reads the one text. On the screens, a card's short "where" is found by looking inside the address for a postcode (`src/lib/address.js`), and falls back to the last part of the address (usually the town) when there is none. A booking begun in the browser before this change has its four boxes put together into the new one when it is opened, so nothing typed is lost.

**Limits, on purpose:** The old four columns (and the postcode check that went with them) still exist for now, empty for new addresses, so that the live site keeps working whichever is updated first. Step two, a small clean-up that removes them and the code that fills them, comes once the new screens have been live for a day or so. A wrongly typed postcode is no longer caught. Nothing in pricing or availability depended on it (travel fees and areas are chosen, not worked out from a postcode). Directions open the whole address in Google Maps as it is written.

**If it ever has to be taken back:** the header of the migration lists what to run: drop the new columns and the two triggers, make the four old columns required again, and run the previous definitions of the functions it replaces. Do this only before step two, and put the old screens back first.

## ADR-060 — Booking boxes in the Admin are sage when settled and sand while they wait (2026-10-19)

**Decision:** Everywhere the Admin sees a booking as a box, its colour says where it stands. **Sage** (a pale green) means settled: confirmed and paid, or confirmed with its cash approved. **Sand** (a pale warm yellow) means still waiting on money or on the Admin's say: awaiting a transfer, a payment to check, cash to approve, or confirmed with the transfer still to come. Each is a pale tint with a darker edge and rail, the text darkened to match, and a pill a little deeper than the tint. Completed, cancelled and no-show bookings keep the colours they had, and a cancelled booking with money still to sort out keeps its sand pill. Colour never carries the meaning alone: the pill's words do, and a pill for something the client has to do keeps its hollow dot, so who has to act can still be told apart without colour. One function, `bookingState` in `calendarPresentation.js`, decides a booking's words and colour, and every view takes them through two names, `getBookingStatusLabel` and `getBookingCardVariant`, so the same booking looks the same in the Agenda, the Day view, a day's own page, the booking sheet, To check, a client's list of bookings, the repeat's list of dates and the clash warnings.

**Reason:** The owner asked that colouring and labels be identical in every calendar view, from shared helpers rather than a copy in each view (brief of 2026-10-18), and then sent the colours they wanted: sage for confirmed and paid, a warm sand for what is waiting on money or on them, with the text darkened to match so it reads on a phone in sunlight.

**How it was built:** The colours are tokens in `src/index.css` (`--sage-*` and `--sand-*`), and `src/theme.test.js` checks that the words on them keep their contrast (4.5:1) and that the rails stand out (3:1). `admin.css` draws a box from the colours its variant sets once; the Agenda and Day cards, a day's own page, To check and a client's list of bookings read them, and the pill colours are set for the Admin only. A client's list of bookings now shows the same pill words as the cards (it used to print the status and the payment status one after the other, so a booking waiting for a transfer read "Awaiting transfer · Awaiting transfer"), and the clash warnings and the repeat's list use the same words, by status alone when that is all they know. No database change.

**Limits, on purpose:** Only the Admin's boxes change. The client's own pages (Your bookings, the confirmation) keep the colours they have. A booking the Admin made herself with "payment pending" still reads "Confirmed · Awaiting transfer": it is confirmed (the time is held for the client) with the money still to come, and it is drawn sand because of the money. A pale card hovered or pressed gets a slightly deeper tint, never white.

**If it ever has to be taken back:** revert the change; nothing in the database depends on it.

## ADR-061 — Every day in the Calendar says its working hours, as the booking engine reads them (2026-10-19)

**Decision:** Every day the Agenda lists says its working hours under its date: usual hours as a plain line ("Hours 14:30–21:00", with "first appointment at 12:00" when that is set), special hours with their highlight as before, and a day off as "Day off", or with its name ("Day off · Christmas Holidays"). With Show every day on, the empty days say their hours too ("free · 14:30–21:00"). The Day view's line says the same. The hours come from one read-only database function, `admin_day_hours(from, to)` (one row per date, Admin only, up to a year), built on `day_hours(date)`, which reads a date's hours the way the booking engine does: its special day if it has one, otherwise the usual week; it also names a block that covers the whole day. The screens show what it says and work none of it out.

**Reason:** Vadim's admin UI notes (Part A §1, `docs/admin-ui-notes.md`): working hours on every day, from the same source the booking engine uses, never different from what clients can book, with no rules copied into React.

**How it was built:** Migration `20261105100000_day_hours.sql` adds the two functions; the booking engine (`compute_booking_availability`) is not touched, so how times are offered does not change. The database test `day_hours.test.sql` checks each kind of day and that the engine agrees: nothing is offered on any day the Calendar calls a day off, and every time offered lies inside the day's hours. The Agenda and the Day view read the function instead of the special-day and usual-week tables (the day's settings page still reads those rows, because it edits them).

**If it ever has to be taken back:** put the screens back, then drop `admin_day_hours(date, date)` and `day_hours(date)`.

## ADR-063 — The booking sheet can share a booking's details, mainly to the client on WhatsApp (2026-10-19)

**Decision:** A share button at the top right of the booking sheet, beside the date and time, offers **WhatsApp client** (WhatsApp opens at the client's own chat with the details written in; hidden when the booking has no usable phone number) and **Share…** (the phone's share sheet; on a computer the text is copied and the screen says "Copied"), and **Copy** (always there: puts the same text on the clipboard). The message is WhatsApp plain text: a *bold* first line with the date and time, the address, the treatments with the total length and price, and the payment in plain words; while a bank transfer is still due it adds the bank details and reference the client's own booking page shows. It never includes the Admin's notes, the client's own phone or email, internal ids or the booking's history. A cancelled booking has no share button. Nothing is sent by itself; the text can be changed in WhatsApp before sending.

**Reason:** Vadim's admin UI notes (Part A §3). Drawn and approved on 2026-10-19 (cancelled bookings: the share icon is hidden, the brief's first option).

**How it was built:** No database change. The message is made in one place, `src/admin/shareBooking.js` (`shareText`), used by both actions; the bank details come from the same function and setting the client's page uses (`get_bank_details`, `bankFromSettings`, `chooseBank`). The button is `ShareBooking.jsx`. When the app becomes a phone app (Capacitor) the Share… action can use its Share plugin; the button stays the same.
